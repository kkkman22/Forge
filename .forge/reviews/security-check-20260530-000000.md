## Layer 3: security-check Review

### P0 Issues
None

### P1 Issues
- **P1-1**: Path traversal in `getCachePath()` — `filename` parameter accepts arbitrary strings including `../` sequences. Current callers use hardcoded filenames, but the API is export-grade and could be misused in future. Attack scenario: caller passes user-influenced filename, causing writes outside plugin data dir.
- **P1-2**: Unsantized `CLAUDE_PLUGIN_DATA` env var used as base directory for file creation. In shared workspace or CI environments where env vars can be influenced, this allows redirecting cache writes to arbitrary filesystem locations.

### P2 Issues
- **P2-1**: Cache files created with default permissions (umask-dependent). No explicit restrictive mode on `mkdirSync` or `writeFileSync`. Cache contains evolved rules text (injected into LLM context) and violation records.
- **P2-2**: Cache JSON parsed without schema validation in `inject-evolved-rules.mjs`. Tampered cache → prompt injection via `additionalContext`.
- **P2-3**: `JSON.parse` on raw `--event` argument in `knowledge-hook-dispatch.mjs` without size/schema validation.

### P3 Issues
- **P3-1**: Violation cache grows without bound in `record-evolved-rule-violation.mjs`.

### Summary
Two P1 path traversal risks in the core `plugin-data-path.mjs` module: unsanitized `filename` parameter and unsanitized `CLAUDE_PLUGIN_DATA` env var. Three P2 issues around file permissions, cache validation, and JSON parsing. No hardcoded secrets, no SQL/command injection, no unsafe dependency additions found.
