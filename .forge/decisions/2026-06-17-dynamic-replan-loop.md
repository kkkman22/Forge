# Decision: 动态重规划闭环（build 失败反馈回 plan）

> 来源：掘金《Loop Engineering 深度实践指南》(2026) §2「计划-执行双层循环 + 动态重规划」。
> 触发：作为 loop-engineering-adoption PR #98 的后续方向评估。

## Product Definition

**Problem**：Forge 当前 build 失败后只做"修复"不"重规划"——three-strike 触发 `/forge debug` 修当前问题，但 debug 的洞察不反馈回 plan 修订剩余 step。复杂任务里，一个失败往往意味着后续多个 task 的假设已失效，仅修当前点会导致连锁返工。

**Users**：跑 standard/full tier 的 Forge 用户，尤其是多 task 的 build 任务。Light tier（单文件小改）几乎用不到重规划。

**Success Criteria**：
- build 中某 task 因"剩余计划假设失效"失败时（非单纯 bug），系统能识别并修订剩余 task 的顺序/拆分/方案，而非只修当前点。
- 重规划后产出修订后的剩余计划（可被人 review），而不是静默改方向。
- 不破坏现有 three-strike → debug 的修复路径（重规划是 debug 之上的"方向修正"层，非替代）。

**Scope Boundaries**：
- ❌ 不做"全量重新 plan"——重规划只修订**剩余未执行**的 task，已完成的 commit 不回滚。
- ❌ 不做实时流式重规划（掘金 §3 流式方向，产品形态不匹配）。
- ❌ 不引入外部状态机框架（LangGraph/Temporal，分发摩擦致命）。
- ❌ 不改 three-strike 的触发阈值和 debug agent 本身。

## Technical Solution

**Tech Selection**：在现有 `triggerThreeStrikeReroute`（`src/spec-pbt-derivation.ts`）+ `buildThreeStrikeDebugReroute`（`src/build.ts`）基础上，加一个 **replan hook**：debug 完成后，读 debug 诊断（`.forge/debug/<topic>.md` 的 fail_signature + 根因），若根因属于"计划假设失效"类（如依赖的接口不存在、方案与现有架构冲突），则触发一次轻量 inline replan——只重写 `.forge/plans/<topic>.md` 中**剩余未完成**的 task。

判定"计划假设失效 vs 单纯 bug"：扩展 `analyzeFixAttempts` 返回的 `fail_signature`，新增 `failure_class ∈ {bug, assumption-violation, environmental}`。只有 `assumption-violation` 才触发 replan；`bug` 走原 debug 修复路径。

**Risks**：
- **重规划误判**（把普通 bug 当假设失效，频繁打乱计划）：影响中等。缓解：`failure_class` 判定保守化，默认归 `bug`，只有明确的方案冲突才归 `assumption-violation`；replan 产出需用户 review（不静默改方向）。
- **replan 本身又错**（重规划引入新问题）：影响中等。缓解：replan 只修订剩余 task，不改已 commit 的；受 plan phase 的 Spec Lock 门禁约束。
- **context 膨胀**（debug + replan 双重消耗）：影响低。缓解：debug 诊断用 write-and-discard，只把 fail_signature + 根因摘要喂给 replan。

**Scalability**：多 task 复杂任务受益最大；单 task 任务 replan 无剩余可改，自动 no-op。零额外基础设施。

**Compatibility**：完全复用现有 three-strike / debug / plan 基建，新增的只是 debug→plan 的反馈链路 + `failure_class` 字段。与 loop-engineering-adoption 的 commit-narrative 无冲突（重规划也是一次"为什么改方向"的叙事，可写进 narrative）。

## Security Assessment

**OWASP Check**：
- **A04 不安全设计**：低风险——replan 修订计划文件，不改代码执行权限。
- **A08 软件/数据完整性**：低风险——replan 受 plan phase Spec Lock 门禁 + frozen-zone 保护（`.forge/plans/` 在受保护区，只追加式修订）。

**STRIDE Analysis**：
- **Tampering（篡改）**：replan 改 `.forge/plans/<topic>.md`。缓解：受保护区只追加、Spec Lock 门禁、用户 review。
- **Denial of Service**：恶意/错误的 fail_signature 反复触发 replan 消耗额度。缓解：replan 触发次数受 three-strike 已有的重试上限约束；replan 本身失败不级联。

**Conclusion**：无显著新增安全风险。核心是受 plan phase 既有门禁保护。

## Veto Record

- **Veto: 全量重新 plan**——回滚已完成 commit 代价过高，违反 Forge 原子提交原则。
- **Veto: 引入 LangGraph/Temporal 状态机**——分发摩擦致命，与 Forge 插件形态冲突。

## 决策结论

**做。Standard tier。** 作为 loop-engineering-adoption 的**后续独立 spec**（不并入当前 PR #98），因为：
1. 涉及 build/plan 引擎核心改动（`failure_class` + replan hook），风险高于当前 PR 的三块纯增量。
2. 独立 spec 可单独 review/test，避免 PR #98 scope 膨胀。
3. 当前 PR 的 R3 commit-narrative 正好能为 replan 提供"为什么改方向"的叙事载体——两者天然衔接但应分步交付。
