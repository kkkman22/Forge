## Product Perspective

**优先级排序(高→低)**:REQ-07 ≈ REQ-01 > REQ-06 > REQ-03 > REQ-04 ≈ REQ-05

- REQ-01(撤销 state-machine T-01):**必交付**。approved spec 的 T-01 前提被证伪却不撤销 = 留下"可执行的危险任务"。撤销成本≈0。
- REQ-06/07(状态体系):**最高 ROI**。status 不可信 → `/forge review`/`ship` 的自动化基础失效。地基级。
- REQ-03:**高价值但非紧急**。防御性工具,当前无人删模块,可延后 T-04 fixture 除外(见 security)。
- REQ-04/05:补齐既有半成品。

**必交付集**:REQ-01/06/07。**尽力交付集**:REQ-03/04/05。
**风险评级**:低。全部只读门禁或文档裁决,无对外行为变更。

## Technical (Architect) Perspective

**REQ-01:选 A(撤销),否决 B(迁移)**。
- 依据 **ADR-0008 #4**:"精简禁止移动被 scripts/src import 的路径"。state-machine 被 `domain/reservations`+`pack/domain-bundle`+`index.ts:132` 生产消费,迁移=改公共 API re-export + pack bundle 组装,违反"行为不变"核心约束。
- Design It Twice 不适用:A/B 收益成本悬殊,无平行设计价值。

**REQ-07 单一事实源**:确认 `requirements.md` 为准。`rebuild-spec-index.mjs` 早已这么读(L145),修复=让 `check-spec-status.mjs` 对齐。**否决引入第三个 spec-level status 字段**——反向复杂化。

**REQ-06**:抽 `resolveSpecStatus(dir)` 共享给两个脚本,防再次口径分叉。

**架构陷阱**:T-11 清野字段 = 全库批量改动(129+132 文件)。约束:git 快照 + INV-7 diff 断言 + **T-11 与 T-09 脚本改造不同 commit**(回滚粒度)。

## Security Perspective

**信任边界(REQ-03)**:dead-code 脚本 grep 纯字符串匹配,禁 eval/正则注入。pack.yaml manifest 内容=不可信数据,仅启发式匹配不执行(符合 §1.9)。

**REQ-04**:`validateArtifactBackedVerdict` 接入 check 不扩大攻击面(本就是 src 可信函数)。PoC 必测畸形 artifact 输入不崩溃(fail-open)。

**REQ-07**:`purge-rogue-status.mjs` **执行后必须自删**,避免遗留"可批量改 frontmatter"工具。防回归用 `check-spec-status.mjs` 内嵌 lint,不依赖独立脚本。

**安全耦合(关键)**:REQ-01 撤销 state-machine 若误判,后果=破坏 domain 参考实现。REQ-03 T-04 反向回归 fixture 是对冲。**约束:T-04 fixture 必须与 T-01 裁决同批落地**。
