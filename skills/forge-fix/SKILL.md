# /forge fix — 修复引擎

> **触发方式**：路由器判定 WorkNature=bugfix 时自动进入，用户入口仍为 `/forge`
> **职责**：通过三阶段流程（analyze → apply → verify）执行结构化 Bug 修复，确保根因定位和验证闭环
> **输出路径**：`.forge/findings/fix-analysis.md`（分析结果）+ `.forge/findings/fix-note.md`（修复记录）+ 代码变更

---

## 1. 概述

`/forge fix` 是 Forge 工作流中专门处理 Bug 修复任务的 SKILL。当路由器通过 WorkNature 维度判定任务为 bugfix 性质时，自动分流到此工作流。用户无需记忆独立命令——入口仍然是 `/forge`。

**核心原则**：先定位根因，再定点修复，最后验证闭环。不靠推测修 bug，不做范围外改动，不跳过验证。

**触发方式**：由路由器 WorkNature=bugfix 自动分流。路由器通过关键词匹配（bug、报错、异常、崩溃、不工作、修复、fix、error、crash、broken、not working）识别 bugfix 任务。用户也可通过 `--nature=bugfix` 显式覆盖。

## 2. 三阶段流程

### 2.1 Analyze 阶段（fix-analyze）

**职责**：通过实际读代码定位根因，产出结构化分析报告。

**产出**：`.forge/findings/fix-analysis.md`

**分析五步**：

| 步骤 | 动作 | 产出 |
|------|------|------|
| 1. 定位 | 用 Grep/Glob 搜索相关代码，记录 file:line | 问题代码位置 |
| 2. 还原 | 追踪正常路径 vs 失败路径的分叉点 | 失败路径描述 |
| 3. 确认 | 分类根因（逻辑/状态/数据/并发/配置/缺防御） | 根因分类 |
| 4. 评估 | 评估影响面（哪些模块/功能受影响） | 影响面清单 |
| 5. 方案 | 提出 2-3 种修复方案 + 推荐 | 方案选项 |

**分析报告格式**：

```markdown
---
topic: "<主题>"
date: "YYYY-MM-DD"
status: "analyzed"
---

## 问题定位

- **位置**：`<file>:<line>`
- **失败路径**：<正常 vs 失败的分叉描述>

## 根因分析

- **分类**：<逻辑/状态/数据/并发/配置/缺防御>
- **根因**：<具体描述>

## 影响面评估

- <受影响的模块/功能 1>
- <受影响的模块/功能 2>

## 修复方案

### 方案 A（推荐）
- **描述**：<方案描述>
- **改动文件**：<文件列表>
- **风险**：<风险评估>

### 方案 B
- **描述**：<方案描述>
- **改动文件**：<文件列表>
- **风险**：<风险评估>
```

**双模式行为**：

| 模式 | 行为 | ConfirmationPoint |
|------|------|------------------|
| interactive | 展示分析结果和方案，等待用户选择方案 | `fix_analyze_confirm` |
| autonomous | 自动选择推荐方案 | `fix_analyze_confirm`，preset: `auto-recommend` |

### 2.2 Apply 阶段（fix-apply）

**职责**：按选定方案执行定点修复。

**范围约束规则**：

- **只改 analyze 中声明的文件**——不允许范围外改动
- 如果发现需要改动 analyze 未声明的文件，回到 analyze 阶段更新分析
- 每个改动必须有明确的根因关联

**流程**：

1. 按方案中的改动文件列表逐文件修复
2. 每个文件修改后运行相关测试
3. 所有修改完成后运行全量验证

### 2.3 Verify 阶段

**职责**：执行验证清单，确认修复有效且无副作用。

**验证清单**：

| # | 验证项 | 方法 | 通过标准 |
|---|--------|------|---------|
| 1 | **复现验证** | 按原始复现步骤执行 | 问题不再出现 |
| 2 | **期望验证** | 验证修复后的期望行为 | 行为符合预期 |
| 3 | **影响面回归** | 运行影响面相关的测试 | 无回归 |
| 4 | **全量测试** | 运行项目完整测试套件 | 全部通过 |

**产出**：`.forge/findings/fix-note.md`

**双模式行为**：

| 模式 | 行为 | ConfirmationPoint |
|------|------|------------------|
| interactive | 展示验证结果，等待用户确认修复完成 | — |
| autonomous | 自动执行验证清单 | `fix_apply_verify`，preset: `auto-verify` |

## 3. 日志调试升级机制

当修复未生效（verify 阶段验证失败）时：

### 升级流程

```
修复未生效
    │
    ▼
切换到日志调试模式（第 1 轮）
  → 在关键路径添加日志
  → 运行复现步骤
  → 分析日志输出
  → 调整修复方案
  → 重新 apply + verify
    │
    ▼ 仍失败
第 2 轮日志调试
  → 扩大日志范围
  → 重新分析
  → 调整修复
    │
    ▼ 仍失败
回到 analyze 阶段
  → 重新做根因分析
  → 可能是根因判断错误
```

**规则**：
- 日志调试最多 2 轮
- 2 轮后仍失败 → 回到 analyze 阶段重新分析
- 日志调试完成后清理添加的日志代码

## 5. 快速通道（Tier=light）

当路由器判定 Tier=light 且 WorkNature=bugfix 时，走快速通道。

### 判定条件

- AI 读代码后能一眼确定根因
- 修复涉及 file:line + 1-2 处改动
- 无跨模块风险

### 流程

跳过 analyze 阶段，直接进入 apply：

```
fix-apply → review
```

快速通道下，apply 阶段直接根据任务描述和代码阅读执行修复。仍需运行验证。

## 8. 已知 AI 失败模式

以下是 Bug 修复阶段最常见的 AI 失败模式。在执行过程中，如果你发现自己正在做以下任何一件事——**立即停下来**。

### 失败模式 1：不读代码就猜根因

**错误行为**：根据错误信息或任务描述直接推测根因，不实际读取相关代码文件，不追踪执行路径。

**为什么这是错的**：推测的根因大概率是错的。错误信息只是症状，不是原因。不读代码就修复等于在黑暗中射击——即使偶尔命中，你也不知道为什么命中，无法确认修复的完整性。

**正确做法**：严格执行分析五步（§2.1）。用 Grep/Glob 定位相关代码，追踪正常路径和失败路径的分叉点，确认根因后再制定方案。每个分析结论都必须有 file:line 引用支撑。

### 失败模式 2：修复范围外的代码

**错误行为**：在修复 bug 的过程中"顺手"重构了旁边的代码，或者修改了 analyze 阶段未声明的文件。

**为什么这是错的**：范围外的改动没有经过根因分析，可能引入新的 bug。§2.2 明确要求"只改 analyze 中声明的文件"。范围外改动也会干扰 review 阶段的评审——评审者无法区分哪些是修复改动，哪些是"顺手"改动。

**正确做法**：只修改 analyze 报告中声明的文件。如果发现需要改动其他文件，回到 analyze 阶段更新分析报告，重新声明改动范围。

### 失败模式 3：跳过验证就声称修复

**错误行为**：修改代码后不运行验证清单（§2.3），直接声称"bug 已修复"。或者只运行了部分验证（如只跑了单元测试，没做复现验证）。

**为什么这是错的**：未经验证的修复声明是谎言。你不知道修复是否真的生效，不知道是否引入了回归。验证清单的四项（复现/期望/影响面/全量测试）缺一不可。

**正确做法**：修复完成后，逐项执行验证清单。每项验证都必须有实际的命令输出作为证据。全部通过后才能声称修复完成。

### 失败模式 4：只修表面症状不修根因

**错误行为**：看到 NullPointerException 就加一个 null check，看到超时就加大超时时间，看到数据不一致就加一个数据修复脚本——只处理症状，不追踪根因。

**为什么这是错的**：表面修复只是把 bug 藏起来了，根因仍然存在。下次换一个触发条件，同样的 bug 会以不同的症状再次出现。分析五步中的"确认根因"（步骤 3）就是为了避免这种情况。

**正确做法**：追踪到根因（为什么会出现 null？为什么会超时？为什么数据不一致？），修复根因而非症状。如果根因修复成本过高，在 fix-note.md 中记录根因和选择表面修复的原因，作为技术债务追踪。
