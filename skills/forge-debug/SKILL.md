# /forge debug — 调试引擎

> **触发方式**：`/forge build` 连续失败 3 次自动触发，或用户直接输入 `/forge debug`
> **职责**：结构化的四阶段根因分析，避免"试试改改"的低效调试方式
> **输出路径**：`.forge/debug/<topic>.md`

---

## 1. 概述

`/forge debug` 以 **Subagent 模式**启动四阶段调试流程，强制按照"调查 → 分析 → 验证 → 修复"的顺序推进。每个阶段有明确的准入和准出条件，阶段之间不可跳跃。

**核心原则**：先理解问题，再解决问题。没有完成根因调查就提出修复方案 = 在黑暗中开枪。

**铁律**：Phase 1 未完成 → 不能提出修复方案。这是不可协商的硬性约束。

---

## 2. 四阶段流程

### Phase 1 — 根因调查（禁止提出修复方案）

**目标**：完整理解问题，建立事实基础。

**执行步骤**：

1. **完整阅读错误信息**：不要只看第一行，完整阅读整个错误栈、日志输出和相关上下文。
2. **稳定复现问题**：找到可靠的复现步骤，确保问题不是偶发的。
3. **检查最近变更**：查看最近的 Git 提交、文件变更，定位可能引入问题的变更。
4. **追踪数据流**：从输入到输出，追踪数据在系统中的流转路径，找到数据异常的节点。

**输出**：将调查结果记录到 `.forge/debug/<topic>.md`：

```markdown
---
topic: "<主题>"
date: "YYYY-MM-DD"
phase: 1
status: "investigating"
---

## 错误信息

<完整的错误信息和上下文>

## 复现步骤

1. <步骤 1>
2. <步骤 2>
3. <步骤 3>

## 最近变更

- <commit hash>: <变更描述>

## 数据流追踪

<数据流转路径和异常节点>

## 初步假设

- 假设 1: <描述>
- 假设 2: <描述>
```

**Phase 1 的铁律**：

```
🚫 Phase 1 未完成，不能提出修复方案。

当前状态：根因调查中
已完成：错误阅读 ✅、复现 ✅
未完成：最近变更检查、数据流追踪

请先完成所有调查步骤。
```

### Phase 2 — 模式分析

**目标**：通过对比和历史经验缩小根因范围。

**执行步骤**：

1. **对比正常代码**：查找类似的、正常工作的代码，对比差异。
2. **搜索已知失败模式**：在 `.forge/knowledge/known-failures.md` 中搜索是否有匹配的已知失败模式。如果匹配到，直接展示历史解决方案，避免重复调查。
3. **搜索历史踩坑记录**：在 `.forge/knowledge/solutions/` 中搜索相关的踩坑记录和解决方案。
4. **模式匹配**：将当前问题与已知的问题模式进行匹配。

**输出**：更新 `.forge/debug/<topic>.md`，追加模式分析结果：

```markdown
## 模式分析

### 已知失败模式匹配

- ✅ 匹配：known-failures.md > "模块导入路径在 monorepo 中解析失败"（置信度：0.8）
  - 历史解决方案：在 vitest.config.ts 中添加 resolve.alias 映射
  - 出现次数：3

### 正常代码对比

<正常代码 vs 问题代码的关键差异>

### 历史踩坑匹配

- 匹配：.forge/knowledge/solutions/timeout-handling.md（相似度：高）
  - 历史问题：异步操作未设置超时
  - 历史解决方案：添加超时机制 + 重试逻辑

### 缩小后的假设

- 假设 A（最可能）: <描述>
- 假设 B: <描述>
```

### Phase 3 — 假设验证

**目标**：逐一验证假设，找到真正的根因。

**执行规则**：

1. **每次只验证单一假设**：不要同时修改多个地方，否则无法确定哪个修改解决了问题。
2. **每次只做最小改动**：改动越小，越容易判断效果。
3. **3 次失败停止**：同一假设连续验证失败 3 次 → 停止修复，质疑架构。

**3 次失败停止规则**：

```
🚫 同一假设连续验证失败 3 次

假设："数据库连接超时导致查询失败"
  尝试 1：增加连接超时时间 → 失败
  尝试 2：添加连接池预热 → 失败
  尝试 3：切换连接池实现 → 失败

停止修复。当前假设可能是错误的，或者问题的根因更深层。
建议与开发者讨论：
  1. 是否需要重新审视架构？
  2. 是否有其他未考虑的因素？
  3. 是否需要引入外部专家？
```

**输出**：更新 `.forge/debug/<topic>.md`，追加验证结果：

```markdown
## 假设验证

### 假设 A：<描述>

| 尝试 | 改动 | 结果 |
|------|------|------|
| 1 | <最小改动描述> | ✅ 成功 / ❌ 失败（原因） |
| 2 | <最小改动描述> | ✅ 成功 / ❌ 失败（原因） |

**结论**：假设 A 成立 / 不成立
```

### Phase 4 — 修复验证

**目标**：以 TDD 方式实施修复，确保问题解决且无新问题。

**执行步骤**：

1. **RED — 写回归测试**：先写一个能复现问题的测试，运行确认它失败。
2. **GREEN — 实施修复**：写最少的代码让回归测试通过。
3. **确认无新问题**：运行完整测试套件，确认修复没有引入新的问题。

**输出**：更新 `.forge/debug/<topic>.md`：

```markdown
## 修复验证

### 回归测试

- 文件：<测试文件路径>
- 描述：<测试描述>
- RED 结果：FAIL ✅（预期失败）

### 修复实施

- 文件：<修改文件路径>
- 改动：<改动描述>
- GREEN 结果：PASS ✅

### 全量测试

- 运行命令：<测试命令>
- 结果：<N> tests passed, 0 failed ✅
- 无新问题 ✅
```

**修复完成后**：

```markdown
---
topic: "<主题>"
date: "YYYY-MM-DD"
phase: 4
status: "resolved"
---
```

### 知识沉淀提示

Phase 4 修复验证通过、status 更新为 `"resolved"` 后，输出一句话提示：

```
💡 要记录这个解决方案吗？（输入 /forge learn 或跳过）
```

**Mode 判断**：如果 `.forge/status.md` 中 `mode` 为 `autonomous`，跳过此提示（autonomous 模式下 learn 阶段由 Skill Scheduler 按 tier=full 自动调度）。

> 此提示不阻塞工作流完成——它是在调试流程正式结束后的附加建议，用户说"不用"或不响应时立即跳过。

## 3. 红旗信号列表

以下信号表明调试方向可能有误，需要停下来重新评估：

| 红旗信号 | 含义 | 建议行动 |
|---------|------|---------|
| 修复一个问题引入两个新问题 | 根因未找到，在治标不治本 | 回到 Phase 1 重新调查 |
| 同一假设连续失败 3 次 | 假设可能是错误的 | 停止修复，质疑架构 |
| 修复代码越来越复杂 | 可能在错误的抽象层解决问题 | 考虑更高层的架构变更 |
| 无法稳定复现问题 | 可能是竞态条件或环境问题 | 增加日志，收集更多数据 |
| 错误信息与代码逻辑不匹配 | 可能看错了错误源 | 重新追踪数据流 |
| 修复后测试通过但行为仍然异常 | 测试可能不够充分 | 补充更多测试场景 |

## 5. 边界情况处理

### 5.1 问题无法复现

如果问题无法稳定复现：

```
⚠️ 问题无法稳定复现

已尝试 5 次复现，成功 2 次、失败 3 次。
可能是竞态条件或环境相关问题。

建议：
1. 增加详细日志，收集更多运行时数据
2. 检查是否有并发访问或时序依赖
3. 对比成功和失败时的环境差异
```

### 5.2 Phase 1 中尝试提出修复

如果在 Phase 1 中尝试跳到修复：

```
🚫 Phase 1 未完成，不能提出修复方案。

你还没有完成根因调查。在没有充分理解问题之前提出修复方案，
很可能只是在治标不治本。

请先完成：
  ❌ 检查最近变更
  ❌ 追踪数据流

完成后再进入 Phase 2。
```

### 5.3 所有假设都失败

如果所有假设在 Phase 3 中都被否定：

```
⚠️ 所有假设均已被否定

已验证的假设：
  ❌ 假设 A：数据库连接超时
  ❌ 假设 B：缓存数据过期
  ❌ 假设 C：权限配置错误

建议：
1. 回到 Phase 1，重新收集信息
2. 扩大调查范围，检查之前忽略的组件
3. 与开发者讨论，可能需要外部视角
```

### 5.4 无 `.forge/` 目录

提示先运行初始化：

```
⚠️ 未检测到 .forge/ 目录。请先运行 forge init 初始化项目。
```

## 6. 示例

### 示例 1：完整四阶段调试

```
$ /forge debug

━━━ Phase 1 — 根因调查 ━━━

📖 完整阅读错误信息...
  TypeError: Cannot read properties of undefined (reading 'map')
  at ExportService.processOrders (src/services/export.ts:42)
  at async ExportController.handleExport (src/controllers/export.ts:18)

🔄 稳定复现...
  复现步骤：POST /api/export { dateRange: "last-7-days", status: null }
  复现率：100%（status 为 null 时必现）

📝 检查最近变更...
  commit abc1234: "feat: add status filter to export"
  — 新增了 status 过滤逻辑，但未处理 null 值

🔍 追踪数据流...
  请求 → Controller → Service.processOrders(orders)
  orders = db.query({ status: null }) → 返回 undefined（而非空数组）

✅ Phase 1 完成

━━━ Phase 2 — 模式分析 ━━━

📊 对比正常代码...
  正常：db.query({ status: "completed" }) → Order[]
  异常：db.query({ status: null }) → undefined

📚 搜索历史踩坑...
  匹配：null-parameter-handling.md (confidence: 0.7)
  历史方案：在查询层统一处理 null 参数

假设 A（最可能）：db.query 在 status=null 时返回 undefined 而非空数组

━━━ Phase 3 — 假设验证 ━━━

验证假设 A：db.query null 处理
  改动：在 query 方法中添加 null 参数检查
  结果：✅ 问题消失

━━━ Phase 4 — 修复验证 ━━━

🔴 RED — 回归测试
  test("should return empty array when status is null")
  结果：FAIL ✅（预期失败）

🟢 GREEN — 实施修复
  在 db.query 中添加：if (params.status === null) delete params.status
  结果：PASS ✅

🧪 全量测试
  42 tests passed, 0 failed ✅
  无新问题 ✅

✅ 问题已解决
  根因：db.query 未处理 null 参数，返回 undefined
  修复：在查询层统一过滤 null 参数
  回归测试：已添加

💡 要记录这个解决方案吗？（输入 /forge learn 或跳过）
```
