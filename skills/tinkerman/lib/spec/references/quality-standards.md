# Quality Standards — Spec 自检维度详解

自检在 Step 2 Review 中执行，未通过则自动修正并重新自检。反复失败 3 次则呈现问题给用户。

## 4.1 Testability

每个需求至少一个可测试场景，格式：

```
当 <前置条件/触发动作>，则 <可观测的预期结果>
```

- 合格：`当用户提交空表单，则显示"请填写必填字段"`
- 不合格：`系统应该有良好的错误处理`（不可测试）

## 4.2 Behavior, Not Implementation

- **禁止**：类名 / 函数名 / 库名 / 表名 / 具体技术方案
- **允许**：用户可见行为 / 业务规则 / 性能约束 / 输入输出契约

## 4.3 Brownfield Delta

棕地开发必须包含 Delta 章节：

- **新增**：本次新增的能力
- **修改**：本次修改的现有能力
- **不变**：明确声明保持不变的行为（防 build 误改）

触发棕地判定的信号：已有代码库、修改现有功能、specs/ 中已有其他规格。

## 4.4 Two-part Structure (Current State / Proposed Change)

必须包含：

- **Current State**：`file:line` 引用 + 当前行为。AI 必须先读代码，不得凭推测填写。
- **Proposed Change**：要改变的 + 明确不改变的。

"明确不改变的"条目是防漂移关键——列出用户可能误以为"顺便改掉"的邻近能力。

## 4.5 Reversibility

必须包含：

- **Rollback Checklist**：回滚步骤清单
- **Mount Points**：本次改动挂载在现有代码/数据上的位置

提前思考可卸载性帮助发现隐藏耦合与副作用。

## 4.6 Anti-drift 声明

反漂移声明三项必填：

- **主目标**：一句话描述核心目标
- **非目标代理信号**：哪些容易被误认为"顺便做了会更好"的相邻工作不做
- **验证材料角色**：怎样的证据才算"需求满足"
