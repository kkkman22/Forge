# Review Checker 共享词汇 / Shared Vocabulary

> **Single Source of Truth** for the 3 review checkers (spec-check / quality-check / security-check)。
> harness 不支持 agent 文件导入；各 checker 在 Step 0 通过 Read 加载本文件。
> 对应 spec: mattpocock-skill-craft-borrow R8（review shared-vocabulary single-source）。
>
> **抽取原则**：仅收录三 checker **verbatim 或 near-verbatim** 的共享脚手架。各 checker 独有的 Severity Judgment 表、check 维度列表、Confidence 抑制阈值**不**在此处——它们是刻意分化的，保留在各 checker。

## 调用约定

每个 checker 在 Step 0（forge_git 之后、主检查之前）执行：

```
Read skills/tinkerman/lib/review/references/shared-vocabulary.md
```

该 Read 计入 checker 的 Read 预算（共享预算为 4 次：1 次本文件 + 3 次存疑项深查）。

---

## 1. Two-Phase Execution Model

所有 checker 的 turn 预算分两阶段执行：

**Phase A: Collect (工具调用阶段)**
- 正常执行评审，收集发现
- 优先执行高优先级检查（P0/P1 相关）
- 当工具调用次数达到 maxTurns - 2 时，立即停止收集

**Phase B: Report (纯输出阶段)**
- **禁止**调用任何工具
- 将收集到的发现填入结构化报告模板
- 输出完整的 `<!-- REPORT_START -->` ... `<!-- REPORT_END -->` 段落

## 2. Structured JSON Finding Schema

每个 finding 的 JSON 字段（三 checker 共享字段集）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `reviewer` | string | reviewer 名（spec-check / quality-check / security-check） |
| `id` | string | finding 唯一 id |
| `title` | string | 问题标题 |
| `severity` | P0\|P1\|P2\|P3 | 严重度（各 checker 的 Severity Judgment 表定义映射，见各 checker） |
| `confidence` | Confidence_Anchor | 0 / 25 / 50 / 75 / 100 |
| `file` | string | 文件路径 |
| `line` | number\|null | 行号 |
| `evidence` | string | 证据（引用 diff/代码片段） |
| `suggested_fix` | string | 修复建议 |
| `autofix_class` | enum | 自动修复分类 |
| `owner` | string | 责任方 |

## 3. Step 0.6 — Known-failures Append-block (YAML)

当输出 P0 或 P1 issue 时，同时输出 known-failures append-block：

```yaml known-failure
pattern_id: <auto-generated-slug>
severity: P0|P1
first_seen_commit: <current-HEAD>
signature: <1-line issue description>
fix_required: <fix suggestion>
```

## 4. 结果返回协议 (Subagent Return Format)

Subagent 的最终返回文本**限制在 800 chars 以内**，格式：

```
status: <pass|fail>
findings: <total_count>
p0: <count>
p1: <count>
report: <path-to-full-report-markdown>
```

`report` 字段指向编排层写入的完整报告文件路径。超出 800 chars 的部分编排层截断。

## 5. Findings-Only Output Constraint

最终输出**必须**是紧凑的 findings-only 格式。编排层会将完整报告写入文件，checker 只需返回 severity table。

**禁止**：前缀散文（"Let me summarize..." / "Based on my analysis..." / "Here are the findings..."）、重复 diff 内容、冗长解释。直接以 `## Layer N` 开头。

## 6. Confidence_Anchor 枚举（共享定义）

| Anchor | 含义 |
|--------|------|
| 100 | certainty / 铁证 |
| 75 | likely / 高置信 |
| 50 | possible / 中等 |
| 25 | weak / 低置信 |
| 0 | guess / 猜测 |

> **各 checker 的抑制阈值不同（刻意分化，不抽取）**：见各 checker 的 Confidence Calibration 小节。

## 不抽取的内容（保留各 checker）

以下内容三 checker **刻意分化**，保留在各 checker 内联，不进本文件：
- **Severity Judgment 表**（spec=需求/scope；quality=错误处理/重复；security=密钥/注入）
- **Check 维度列表**（spec=7 项；quality=8 项；security=6 项）
- **Confidence 抑制阈值**（quality 抑制 ≤50；security 保留 P0@50；spec 抑制 ≤25）
- **Read 预算数字**（各 checker 的 maxTurns 与具体 Read 上限，见各 checker Turn Budget Discipline）
- **check 维度独有的 Step 0.5 Path A/B**（spec-check 独有）

## 维护约定

- 本文件是 SSOT。改本文件的共享块，三个 checker 同步生效。
- 各 checker 的 Step 0 Read 指令 + Read 预算（4 次）是与本文件的契约。
- 若某块从"共享"变为"分化"，从本文件移除并回归各 checker 内联。
