# /forge refactor — 重构引擎

> **触发方式**：路由器判定 WorkNature=refactor 时自动进入，用户入口仍为 `/forge`
> **职责**：通过三阶段流程（scan → design → apply）执行结构化重构，确保行为等价性
> **输出路径**：`.forge/findings/refactor-scan.md`（扫描结果）+ `.forge/plans/refactor-<topic>.md`（执行方案）+ 代码变更

---

## 1. 概述

`/forge refactor` 是 Forge 工作流中专门处理重构任务的 SKILL。当路由器通过 WorkNature 维度判定任务为重构性质时，自动分流到此工作流。用户无需记忆独立命令——入口仍然是 `/forge`。

**核心原则**：重构 = 改变结构，不改变行为。每一步都必须通过测试验证行为等价性。如果测试不存在，先补测试再重构。

**触发方式**：由路由器 WorkNature=refactor 自动分流。路由器通过关键词匹配（优化、重构、重写、拆分、性能改进、代码整理、refactor、optimize、restructure、simplify）识别重构任务。用户也可通过 `--nature=refactor` 显式覆盖。

---

## 2. 前置检查

在启动重构流程之前，必须逐条验证以下 7 项前置条件。**任一条件命中时，不得继续重构**，而是输出结构化拒绝信息并路由到正确的工作流。

### 检查清单

| # | 检查条目 | 验证方法 | 命中时的路由 |
|---|---------|---------|------------|
| 1 | **是否夹带行为改动** | 分析任务描述，判断是否包含新功能或 bug 修复 | → 路由器重新判定为 feature 或 bugfix |
| 2 | **目标是否有测试覆盖** | 检查重构目标文件是否有对应的测试文件 | → 先补测试（`/forge build` 补充测试任务） |
| 3 | **是否跨模块** | 检查重构是否涉及 3 个以上独立模块 | → 先走 `/forge spec` 做设计 |
| 4 | **是否全是风格口味** | 判断候选改动是否全部为命名风格、缩进、格式等 | → 走 lint/formatter 规则配置 |
| 5 | **是否生成产物/第三方代码** | 检查目标文件是否为自动生成或第三方代码 | → 改源头（生成器配置或上游依赖） |
| 6 | **范围是否过大** | 检查涉及文件数是否超过 15 个 | → 缩小范围，分批重构 |
| 7 | **扫完是否有东西可改** | scan 阶段完成后检查候选列表是否为空 | → "零输出合法"，Agent 返回 `should_fully_stop: true` |

### 拒绝输出格式

```
🚫 重构前置检查未通过

命中检查：<检查条目名称>
证据：<具体的文件路径、分析结果或状态>
建议路由：<应该先执行的命令或工作流>
重入条件：<满足什么条件后可以重新运行重构>
```

**示例 — 夹带行为改动**：

```
🚫 重构前置检查未通过

命中检查：是否夹带行为改动
证据：任务描述"重构用户模块并添加邮箱验证"包含新功能（邮箱验证）
建议路由：/forge — 路由器将重新判定为 feature 工作性质
重入条件：将新功能需求拆分为独立任务后，纯重构部分可重新提交
```

### Autonomous 模式行为

当处于 autonomous 模式且前置检查不通过时，Agent 返回：

```json
{
  "success": false,
  "summary": "重构前置检查未通过：<命中检查>",
  "evidence": "<证据>",
  "suggested_route": "<建议路由>",
  "reentry_condition": "<重入条件>"
}
```

## 3. 三阶段流程

### 3.1 Scan 阶段（refactor-scan）

**职责**：扫描代码库，识别优化点，按方法库分类，输出候选清单。

**产出**：`.forge/findings/refactor-scan.md`

**流程**：

1. 读取任务描述，确定重构范围（目标文件/模块）
2. 扫描目标代码，按方法库（§4）四层分类识别候选优化点
3. 为每个候选标注：位置（file:line）、当前问题、建议方法、预估影响、推荐等级（★/☆）
4. 输出候选清单

**Scan 输出格式**：

```markdown
---
topic: "<主题>"
date: "YYYY-MM-DD"
candidates: <数量>
---

## 扫描结果

### L1 — 行为等价迁移

| # | 位置 | 当前问题 | 建议方法 | 推荐 |
|---|------|---------|---------|------|
| 1 | `src/utils.ts:42` | 魔法数字散落多处 | Extract Constant | ★ |

### L2 — Fowler 经典

| # | 位置 | 当前问题 | 建议方法 | 推荐 |
|---|------|---------|---------|------|
| 2 | `src/service.ts:80-120` | 方法过长（40 行） | Extract Method | ★ |

### L3 — 结构拆分

（无候选）

### L4 — 性能

（无候选）

## 推荐执行顺序

1. #1 Extract Constant（低风险，立即可做）
2. #2 Extract Method（中风险，需验证调用方）
```

**双模式行为**：

| 模式 | 行为 | ConfirmationPoint |
|------|------|------------------|
| interactive | 展示候选清单，等待用户勾选要执行的项 | — |
| autonomous | 自动选择所有推荐项（★） | `refactor_scan_select`，preset: `auto-select-recommended` |

### 3.2 Design 阶段

**职责**：为每个勾选的候选项制定详细执行方案。

**产出**：`.forge/plans/refactor-<topic>.md`

**每个候选项的方案包含**：

| 字段 | 说明 |
|------|------|
| 方法名 | 从方法库（§4）中选择的具体方法 |
| 执行步骤 | 逐步操作说明 |
| 退出信号 | 什么情况下应该停止（如：测试开始失败） |
| 验证方式 | 每步完成后运行什么命令验证 |
| 回滚策略 | 如果出问题怎么回退 |

**双模式行为**：

| 模式 | 行为 | ConfirmationPoint |
|------|------|------------------|
| interactive | 展示执行方案，等待用户 review 和批准 | — |
| autonomous | 自动批准方案 | `refactor_design_review`，preset: `auto-approve` |

### 3.3 Apply 阶段（refactor-apply）

**职责**：逐步执行重构方案，每步验证行为等价性。

**流程**：

1. 按方案中的执行步骤逐步操作
2. 每步完成后运行验证命令（测试/lint/typecheck）
3. 验证通过 → 继续下一步
4. 验证失败 → 回滚当前步骤，记录失败原因
5. 所有步骤完成后，运行全量测试确认无回归
6. 执行原子提交

**双模式行为**：

| 模式 | 行为 | ConfirmationPoint |
|------|------|------------------|
| interactive | 每步完成后等待用户放行 | — |
| autonomous | 自动继续，每步跑验证 | `refactor_apply_step`，preset: `continue` |

## 4. 方法库

重构方法按四层分类，scan 阶段按此分类匹配候选，design 阶段每步引用方法名。

### L1 — 行为等价迁移（最低风险）

| 方法 | 说明 | 适用场景 |
|------|------|---------|
| Rename | 重命名变量/函数/类 | 命名不清晰、不一致 |
| Move | 移动函数/类到更合适的模块 | 职责错位 |
| Extract Constant | 提取魔法数字/字符串为命名常量 | 散落的字面量 |
| Extract Type | 提取内联类型为独立类型定义 | 重复的类型声明 |
| Inline | 内联只用一次的变量/函数 | 过度抽象 |

### L2 — Fowler 经典（中等风险）

| 方法 | 说明 | 适用场景 |
|------|------|---------|
| Extract Method | 从长方法中提取子方法 | 方法过长（>30 行） |
| Extract Class | 从大类中提取子类 | 类职责过多 |
| Replace Conditional with Polymorphism | 用多态替代条件分支 | 复杂的 if/switch 链 |
| Introduce Parameter Object | 将多个参数归组为对象 | 参数过多（>3 个） |
| Replace Temp with Query | 用方法调用替代临时变量 | 复杂的临时变量计算 |
| Encapsulate Field | 将公开字段改为 getter/setter | 直接访问内部状态 |

### L3 — 结构拆分（较高风险）

| 方法 | 说明 | 适用场景 |
|------|------|---------|
| Split Module | 将大模块拆分为多个小模块 | 模块职责过多 |
| Split Class | 将大类拆分为多个协作类 | 上帝类 |
| Introduce Facade | 为复杂子系统引入门面 | 调用方需要了解太多内部细节 |
| Extract Layer | 提取独立的抽象层 | 层次混乱 |

### L4 — 性能（需要度量验证）

| 方法 | 说明 | 适用场景 |
|------|------|---------|
| Lazy Loading | 延迟加载非立即需要的资源 | 启动时间过长 |
| Caching | 缓存重复计算的结果 | 重复的昂贵计算 |
| Batch Processing | 批量处理替代逐条处理 | N+1 查询、逐条 API 调用 |
| Memoization | 记忆化纯函数结果 | 相同输入的重复调用 |

## 5. 快速通道（Tier=light）

当路由器判定 Tier=light 且 WorkNature=refactor 时，走快速通道。

### 入场条件

- 单文件重构
- 改动点 ≤ 3 处
- 目标文件有测试覆盖

### 流程

跳过 scan 阶段，直接进入 apply：

```
refactor-apply → review
```

快速通道下，apply 阶段直接根据任务描述执行重构，不需要 scan 产出的候选清单。每步仍需运行验证。

## 8. 边界情况处理

### 8.1 Scan 无候选

```
ℹ️ 扫描完成，未发现需要重构的候选项。

当前代码结构良好，无需重构。
```

Agent 返回 `should_fully_stop: true`，这是合法的零输出。

### 8.2 Apply 步骤验证失败

1. 回滚当前步骤的改动
2. 记录失败原因到 `.forge/findings/`
3. 继续下一个候选项（如有）
4. 如果连续 3 步失败，停止 apply 并报告

### 8.3 无 `.forge/` 目录

```
⚠️ 未检测到 .forge/ 目录。请先运行 forge init 初始化项目。
```

## 9. 已知 AI 失败模式

以下是重构阶段最常见的 AI 失败模式。在执行过程中，如果你发现自己正在做以下任何一件事——**立即停下来**。

### 失败模式 1：夹带行为改动

**错误行为**：在重构过程中"顺手"添加新功能、修复 bug、或改变函数的外部行为。比如在 Extract Method 的同时修改了方法的返回值类型，或者在 Rename 的同时添加了新的参数。

**为什么这是错的**：重构的核心定义是"改变结构，不改变行为"。夹带行为改动意味着测试可能因为行为变更而失败，而你无法区分是重构引入的 bug 还是预期的行为变更。这破坏了重构的安全网。

**正确做法**：严格遵守行为等价原则。如果在重构过程中发现需要修改行为的地方，记录到 `.forge/findings/` 中，留给后续的 feature 或 bugfix 流程处理。每步完成后运行测试，确认行为未变。

### 失败模式 2：不跑测试就重构

**错误行为**：连续执行多步重构操作后才运行测试，或者根本不运行测试就声称"重构完成"。

**为什么这是错的**：测试是重构的安全网。不跑测试就重构等于在没有安全网的情况下走钢丝——你不知道哪一步引入了问题。如果最后测试失败了，你需要逐步回退来定位问题，浪费大量时间。

**正确做法**：每一步重构操作后都运行验证命令。Apply 阶段的流程是：操作 → 验证 → 通过则继续，失败则回滚。没有例外。

### 失败模式 3：一次改太多

**错误行为**：把多个独立的重构操作合并成一个大步骤执行。比如同时做 Extract Method + Rename + Move，或者一次性重构整个模块的所有方法。

**为什么这是错的**：大步骤的重构难以验证、难以回滚、难以 review。如果测试失败，你不知道是哪个操作引起的。原子性是重构安全的基础。

**正确做法**：每步只做一个重构操作，对应方法库中的一个方法。每步有独立的验证和回滚策略。Design 阶段就应该把大重构拆成小步骤。

### 失败模式 4：不用方法库命名

**错误行为**：在 scan 和 design 阶段使用模糊的描述（如"优化一下"、"整理代码"），而不引用方法库中的具体方法名。

**为什么这是错的**：模糊的描述导致 apply 阶段不知道具体要做什么操作，容易偏离预期。方法库中的每个方法都有明确的定义、适用场景和风险等级，引用方法名能确保执行的精确性。

**正确做法**：scan 阶段的每个候选必须标注方法库中的方法名（如 "Extract Method"、"Split Module"）。design 阶段的每个步骤必须引用方法名。如果候选不属于方法库中的任何方法，说明它可能不是重构而是行为改动。
