# /forge spec — 规格引擎

> **触发方式**：全量路径的第二步，用户直接输入 `/forge spec`，或 `/forge spec <file-path>` 导入外部规格
> **职责**：将需求固化为可审阅、可测试、可锁定的规格文档，锁定后成为 build 和 review 的唯一真理源。支持从外部规格文档导入并转化为 Forge 格式。
> **输出路径**：`.forge/specs/<feature>/spec.md`

---

## 1. 概述

`/forge spec` 通过三步流程（Propose → Review → Lock）将模糊的需求转化为结构化的规格文档。规格文档是 Forge 工作流的核心合同——锁定后，build 按它实现，review 按它验收，任何偏离都会被拦截。

**核心原则**：规格描述行为，不描述实现。写"当用户提交表单时，系统返回成功提示"，不写"调用 FormService.submit() 方法"。

---

## 1.5. 导入模式（Import Mode）

当开发者从产品经理处收到外部规格文档时，使用导入模式将其转化为 Forge 格式：

```
/forge spec path/to/external-spec.md
```

**适用场景**：产品经理交付了独立 spec 文档，开发者需要将其纳入 Forge 工作流。

**导入流程**：读取指定路径文档 → 提取需求/场景转化为 Forge 格式 → 复用五项自检（未通过则自动修正）→ 展示转化结果供用户确认 → 写入 `.forge/specs/<feature>/spec.md`（status: "locked"，frontmatter 标注 import_source）。

**转化规则**：

| 提取目标 | 转化策略 |
|---------|---------|
| 目的 | 提取为"目的"章节，说明要解决什么问题 |
| 需求条目 | 拆解为独立条目，带编号和标题 |
| 场景 | 转为"当...则..."格式；叙述性需改写 |
| 不做什么 | 直接映射；未明确时推断并提示用户确认 |
| 反漂移声明 | 自动生成，基于需求推断主目标和非目标信号 |
| Delta | 原文描述对现有功能修改时，提取为 Delta 章节 |

**转化质量保障**：不丢失信息（无法映射的放入"待确认"列表）；不添加信息（新增内容标注"自动生成"）；场景必须可测试；去除实现细节。

**Frontmatter**：导入模式的 spec 增加 `import_source: "<原始文件相对路径>"` 字段。原始文件保留在原位。

导入并锁定后，规格成为标准的 `.forge/specs/<feature>/spec.md`，后续 `/forge plan`、`/forge build`、`/forge review` 流程无需区分来源。

---

## 2. 三步流程

### Step 1：Propose（生成草案）

读取以下上下文，生成规格草案：

| 输入源 | 说明 |
|--------|------|
| `.forge/decisions/` | 已有决策文档（如有），提取产品定义、技术方案 |
| `.forge/config.md` | 项目配置（技术栈、安全级别） |
| `.forge/specs/` | 现有规格，避免重复、确保一致性 |
| 用户输入 | 当前任务的需求描述 |

**生成规则**：

1. **先读代码再写 spec**：AI 必须先读取相关代码文件，理解模块结构、函数签名和行为。不允许未读代码填写 Current State。
2. 从决策文档提取已确认的方向，不重复讨论已决事项。
3. 从现有 specs 识别相关功能，确保不冲突。
4. 将需求拆解为独立条目，每条附带至少一个可测试场景。
5. 棕地开发自动包含 Delta 章节。

草案生成后，向用户展示完整内容，进入 Review 步骤。

### Step 2：Review（自检）

对草案执行以下自检，逐项报告结果：

| 检查项 | 通过标准 |
|--------|---------|
| **可测试性** | 所有需求均有"当...则..."格式的场景 |
| **边界清晰度** | 无模糊用语（如"适当的"、"合理的"） |
| **人类可读性** | 不包含类名、函数名、库名等实现细节 |
| **棕地兼容性** | 棕地项目有完整的新增/修改/不变章节 |
| **反漂移完整性** | 主目标、非目标代理信号、验证材料角色三项已填写 |
| **两段式结构** | Current State 有 file:line 引用；Proposed Change 有变更/不变声明 |
| **可卸载性** | 回滚清单和挂载点清单均已填写 |

**自检输出格式**：

```
📋 规格自检

✅ 可测试性：所有 N 个需求均有可测试场景
✅ 边界清晰度：无模糊用语
✅ 人类可读性：无实现细节泄露
✅ 棕地兼容性：Delta 章节完整（或：非棕地项目，跳过）
✅ 反漂移完整性：主目标、非目标代理信号、验证材料角色均已填写
✅ 两段式结构：Current State 有 file:line 引用，Proposed Change 有变更/不变声明
✅ 可卸载性：回滚清单和挂载点清单已填写

自检通过。确认锁定此规格？(y/n)
```

任一检查项未通过，列出问题并自动修正草案，重新自检直到全部通过。

### Step 3：Lock（锁定）

用户确认后：

1. 将 `status` 从 `"draft"` 改为 `"locked"`
2. 写入 `.forge/specs/<feature>/spec.md`
3. 输出确认：

```
🔒 规格已锁定：.forge/specs/<feature>/spec.md

此规格现在是 build 和 review 的唯一真理源。
后续修改需要先解锁（status 改回 draft），重新走 Review → Lock。

下一步：/forge plan
```

**未锁定时**：用户不确认则保持 `draft`，可继续修改。用户提出修改意见后更新草案并重新 Review。

## 3. Spec 文档格式

### YAML Frontmatter

| 字段 | 类型 | 说明 |
|------|------|------|
| `feature` | string | 功能名称，kebab-case（如 `user-notification`） |
| `status` | string | `draft` 或 `locked` |
| `date` | string | 创建或最后修改日期，YYYY-MM-DD |
| `import_source` | string? | 可选。导入模式记录原始规格文件相对路径 |

### 正文结构

```markdown
---
feature: "<功能名>"
status: "draft"
date: "YYYY-MM-DD"
---

## 目的
<一段话：解决什么问题，为谁解决>

## 需求

### 需求 1：<标题>
<描述行为而非实现>

**场景**：
- 当 <前置条件>，则 <预期结果>

## 场景汇总
| 编号 | 场景 | 对应需求 |
|------|------|---------|

## Current State（当前状态）
<必填。AI 必须先读取相关代码>

### 相关模块
| 模块/函数 | 位置 | 当前行为 |
|-----------|------|---------|

## Proposed Change（计划变更）

### 要改变的
- <变更项>：<描述>

### 明确不改变的
- <不变项>：<原因>

## 不做什么
<明确列出本次不做的事情>

## Reversibility（可卸载性）

### 回滚清单
- <需撤销的改动>

### 挂载点
<所有外部接入点>

## 反漂移声明

### 主目标
<一句话核心目标>

### 非目标代理信号
<不应被优化的指标>

### 验证材料角色
本规格中的场景和示例数据仅用于验证行为正确性，不构成产品需求的一部分。

## Delta（仅棕地开发）
### 新增 / 修改 / 不变
```

## 4. 质量标准

### 4.1 可测试性

每个需求**至少包含一个可测试场景**，使用"当...则..."格式。合格：`当用户提交空表单，则系统显示"请填写必填字段"错误提示`。不合格：`系统应该有良好的错误处理`（不可测试，什么是"良好的"？）。

### 4.2 行为描述，非实现描述

**禁止**：类名、函数名、库名、数据库表名、具体技术方案。**允许**：用户可见行为、业务规则、性能约束。

### 4.3 棕地开发 Delta 章节

棕地开发（在现有代码库上变更）时，规格**必须包含** Delta 章节（新增/修改/不变）。判定信号：项目已有代码库、任务是对现有功能的修改、`.forge/specs/` 中已有其他规格。

### 4.4 "现状→变化"两段式结构

Current State 必须引用具体代码位置（`file:line`），描述当前行为和结构。Proposed Change 必须明确"要改变什么"和"不改变什么"。

### 4.5 可卸载性（Reversibility）

规格**必须包含** Reversibility 部分（回滚清单 + 挂载点清单），提前思考可卸载性能帮助发现隐藏的耦合和副作用。

---

## 5. 门禁：Spec 未锁定 → 阻断 `/forge build`

→ 遵循 CLAUDE.md §2.2 前置检查。标准/全量路径下，`/forge build` 启动前**必须检查** spec 是否锁定。

未锁定时阻断：

```
🚫 Build 阻断：规格未锁定

当前任务的规格状态为 "draft"，需要先锁定规格才能开始 build。
请运行 /forge spec 完成规格的 Review 和 Lock 流程。
规格路径：.forge/specs/<feature>/spec.md
```

**轻量路径例外**：不要求锁定的 spec，直接执行 build。

---

## 6. 执行流程

1. **前置检查**：`.forge/` 目录是否存在。不存在 → 提示先运行 `forge init`
2. **读取上下文**：`.forge/decisions/` → `.forge/config.md` → `.forge/specs/`
3. **Propose**：基于上下文生成规格草案（§2 Step 1）
4. **Review**：自检（§2 Step 2），未通过则自动修正并重新自检
5. **用户确认**：确认 → Lock；修改意见 → 更新草案回 Review；拒绝 → 保持 draft
6. **Lock**：锁定规格（§2 Step 3）

---

## 7. 边界情况处理

| 条件 | 输出 |
|------|------|
| 无 decisions/ 文档 | ℹ️ 未找到决策文档，将直接基于需求描述生成规格。如需决策分析，运行 /forge decide |
| 已有同名 spec (draft) | 读取现有草案作为基础修改 |
| 已有同名 spec (locked) | ⚠️ 已锁定。先改 status 为 draft，再重新运行 |
| 需求描述过于模糊 | 追问：1. 要解决什么问题？2. 目标用户？3. 关键使用场景？ |
| 自检反复不通过（3次） | 停止自动修正，请用户提供更具体的场景描述 |
| 无 `.forge/` 目录 | ⚠️ 请先运行 forge init |
| 导入模式：文件不存在 | ⚠️ 指定的文件不存在 |
| 导入模式：无法提取需求 | ⚠️ 无法提取有效的需求条目 |
| 导入模式：原文含实现细节 | ℹ️ 移除了实现细节，原始文件中不会丢失 |

## 8. 示例

### Canonical：绿地项目

任务："为订单系统添加批量导出功能"

```markdown
---
feature: "order-batch-export"
status: "draft"
date: "2025-01-15"
---

## 目的

为订单管理系统提供批量导出功能，让运营人员按条件筛选并导出订单数据。

## 需求

### 需求 1：按条件筛选导出

运营人员可按时间范围、订单状态、金额范围筛选并导出。

**场景**：
- 当运营人员选择"最近 7 天"并点击导出，则系统生成文件并开始下载
- 当筛选结果为空，则提示"没有符合条件的订单"且不生成文件

### 需求 2：大数据量导出

**场景**：
- 当导出超过 10000 条，则提示"导出任务已提交"并在后台处理
- 当后台导出完成，则发送通知并提供下载链接
- 当下载链接超过 24 小时，则链接失效

## 不做什么

- 不做导出模板自定义（固定格式）
- 不做定时自动导出（仅手动触发）

## 反漂移声明

### 主目标

让运营人员按条件筛选并导出订单数据，大数据量时异步处理。

### 非目标代理信号

- 导出速度优化不是目标，正确性和完整性才是

### 验证材料角色

本规格中的场景和示例数据仅用于验证行为正确性，不构成产品需求。
```

**棕地项目变体**：额外包含 Delta 章节（新增/修改/不变）和 Current State / Proposed Change 两段式结构。详见 §3 正文结构模板。

## 9. 已知 AI 失败模式

| 失败模式 | 错误行为 | 正确做法 |
|---------|---------|---------|
| 不读现有代码就写 spec | Current State 凭推测填写或留空 | 先读取相关代码文件，用 file:line 引用填写 |
| spec 与代码实际结构不一致 | 引用的路径、函数名、行号与实际不匹配 | 每个 file:line 引用都经过实际读取验证 |
| 遗漏"明确不做"边界 | 只写"要做什么" | 在 Proposed Change 列"明确不改变"，在"不做什么"列出用户可能期望但不实现的功能 |
