# /forge spec — 规格引擎

> **触发方式**：全量路径的第二步，或用户直接输入 `/forge spec`
> **职责**：将需求固化为可审阅、可测试、可锁定的规格文档，锁定后成为 build 和 review 的唯一真理源
> **输出路径**：`.forge/specs/<feature>/spec.md`

---

## 1. 概述

`/forge spec` 通过三步流程（Propose → Review → Lock）将模糊的需求转化为结构化的规格文档。规格文档是 Forge 工作流的核心合同——锁定后，build 按它实现，review 按它验收，任何偏离都会被拦截。

**核心原则**：规格描述行为，不描述实现。写"当用户提交表单时，系统返回成功提示"，不写"调用 FormService.submit() 方法"。

---

## 2. 三步流程

### Step 1：Propose（生成草案）

读取以下上下文，生成规格草案：

| 输入源 | 说明 |
|--------|------|
| `.forge/decisions/` | 已有的决策文档（如有），提取产品定义、技术方案、安全评估 |
| `.forge/config.md` | 项目配置（技术栈、安全级别） |
| `.forge/specs/` | 现有规格文档，避免重复定义、确保一致性 |
| 用户输入 | 当前任务的需求描述 |

**生成规则**：

1. **先读代码再写 spec**：在生成草案之前，AI **必须**先读取与需求相关的代码文件，理解当前的模块结构、函数签名和行为。不允许在未读代码的情况下填写"Current State"部分。
2. 从决策文档中提取已确认的产品定义和技术方向，不重复讨论已决事项。
3. 从现有 specs 中识别相关功能，确保新规格与已有规格不冲突。
4. 将需求拆解为独立的需求条目，每个条目附带至少一个可测试场景。
5. 如果项目为棕地开发（现有代码库上的变更），自动包含 Delta 章节。

草案生成后，向用户展示完整草案内容，进入 Review 步骤。

### Step 2：Review（自检）

对草案执行四项自检，逐项报告结果：

| 检查项 | 检查内容 | 通过标准 |
|--------|---------|---------|
| **可测试性** | 每个需求是否有至少一个可测试场景 | 所有需求均有"当...则..."格式的场景 |
| **边界清晰度** | 需求边界是否明确，是否有歧义 | 无模糊用语（如"适当的"、"合理的"、"等等"） |
| **人类可读性** | 非技术人员能否理解规格内容 | 不包含类名、函数名、库名等实现细节 |
| **棕地兼容性** | 棕地项目是否包含 Delta 章节 | 棕地项目有完整的新增/修改/不变章节 |
| **反漂移完整性** | 反漂移声明是否完整 | 主目标、非目标代理信号、验证材料角色三项均已填写 |
| **两段式结构** | 是否包含 Current State 和 Proposed Change | Current State 有 file:line 引用；Proposed Change 有"要改变的"和"明确不改变的" |
| **可卸载性** | 是否包含 Reversibility 部分 | 回滚清单和挂载点清单均已填写 |

**自检输出格式**：

```
📋 规格自检

✅ 可测试性：所有 N 个需求均有可测试场景
✅ 边界清晰度：无模糊用语
✅ 人类可读性：无实现细节泄露
✅ 棕地兼容性：Delta 章节完整（或：非棕地项目，跳过）
✅ 反漂移完整性：主目标、非目标代理信号、验证材料角色均已填写
✅ 两段式结构：Current State 有 file:line 引用，Proposed Change 有变更/不变声明
✅ 可卸载性：回滚清单和挂载点清单已填写

自检通过。确认锁定此规格？(y/n)
```

如果任一检查项未通过，列出具体问题并自动修正草案，然后重新自检，直到全部通过。

### Step 3：Lock（锁定）

用户确认后执行锁定：

1. 将 YAML frontmatter 中的 `status` 从 `"draft"` 改为 `"locked"`。
2. 将规格文档写入 `.forge/specs/<feature>/spec.md`。
3. 输出确认信息：

```
🔒 规格已锁定：.forge/specs/<feature>/spec.md

此规格现在是 build 和 review 的唯一真理源。
后续修改需要先解锁（将 status 改回 draft），修改后重新走 Review → Lock 流程。

下一步：/forge plan
```

**未锁定时的行为**：如果用户不确认（回复 n、否、不等），规格保持 `draft` 状态，可以继续修改。用户可以提出修改意见，Forge 据此更新草案并重新进入 Review。

## 3. Spec 文档格式

### YAML Frontmatter

```yaml
---
feature: "<功能名>"
status: "draft" | "locked"
date: "YYYY-MM-DD"
---
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `feature` | string | 功能名称，kebab-case 格式，如 `user-notification` |
| `status` | string | `draft`（草案）或 `locked`（已锁定） |
| `date` | string | 创建或最后修改日期，YYYY-MM-DD 格式 |

### 正文结构

```markdown
---
feature: "user-notification"
status: "draft"
date: "2025-01-15"
---

## 目的

<一段话说明这个功能要解决什么问题，为谁解决>

## 需求

### 需求 1：<需求标题>

<需求描述，描述行为而非实现>

**场景**：

- 当 <前置条件>，则 <预期结果>
- 当 <前置条件>，则 <预期结果>

### 需求 2：<需求标题>

...

## 场景汇总

<将所有需求中的场景汇总为一个完整的验收场景列表，便于 review 逐条对照>

| 编号 | 场景 | 对应需求 |
|------|------|---------|
| S1 | 当 ...，则 ... | 需求 1 |
| S2 | 当 ...，则 ... | 需求 1 |
| S3 | 当 ...，则 ... | 需求 2 |

## Current State（当前状态）

<**必填**。描述与本次变更相关的代码现状。AI 必须在生成此部分之前实际读取相关代码文件。>

### 相关模块

| 模块/函数 | 位置 | 当前行为 |
|-----------|------|---------|
| <模块或函数名> | <file:line 或文件路径> | <当前行为的简要描述> |
| <模块或函数名> | <file:line 或文件路径> | <当前行为的简要描述> |

### 当前结构概述

<用 1-3 段文字描述相关模块/函数的当前结构和职责划分，引用具体的 file:line 或函数名>

## Proposed Change（计划变更）

<**必填**。明确描述本次要改变什么、不改变什么。>

### 要改变的

- <变更项 1>：<具体描述变更内容>
- <变更项 2>：<具体描述变更内容>

### 明确不改变的

- <不变项 1>：<为什么不需要改>
- <不变项 2>：<为什么不需要改>

## 不做什么

<明确列出本次不做的事情，划清边界>

- 不做 ...
- 不做 ...

## Reversibility（可卸载性）

<**必填**。回答：如果要回滚这个 feature，需要撤销哪些改动？>

### 回滚清单

- <需要撤销的改动 1>
- <需要撤销的改动 2>
- <需要撤销的改动 3>

### 挂载点

<列出 feature 的所有外部接入点。判据：删了这一项，feature 是否从用户/系统视角消失？>

- <挂载点 1>：<说明>
- <挂载点 2>：<说明>

## 反漂移声明

### 主目标

<用一句话描述本次功能的核心目标。后续所有实现和验证都围绕这个目标展开。>

### 非目标代理信号

<列出看起来相关但不应被优化的指标。防止 AI 在执行过程中偏离主目标去优化这些信号。>

- <例：测试覆盖率数字本身不是目标，行为正确性才是>
- <例：代码行数减少不是目标，可维护性才是>

### 验证材料角色

<声明测试数据、示例输入等验证材料的角色——它们是用来验证实现的工具，不是需求本身。防止 AI 将测试用例中的具体值硬编码为产品逻辑。>

声明：本规格中的场景和示例数据仅用于验证行为正确性，不构成产品需求的一部分。

## Delta

<仅棕地开发时包含此章节>

### 新增

- <新增的功能/文件/接口>

### 修改

- <修改的功能/文件/接口>：<变更说明>

### 不变

- <明确不受影响的功能/文件/接口>
```

## 4. 质量标准

### 4.1 可测试性

每个需求**至少包含一个可测试场景**。可测试场景使用"当...则..."格式：

```
当 <前置条件/触发动作>，则 <可观测的预期结果>
```

**合格示例**：

- 当用户提交空表单，则系统显示"请填写必填字段"错误提示
- 当 API 返回 404，则页面展示"未找到"提示并提供返回链接
- 当用户连续 3 次输入错误密码，则账户锁定 15 分钟

**不合格示例**：

- 系统应该有良好的错误处理 ← 不可测试，什么是"良好的"？
- 页面应该快速加载 ← 不可测试，什么是"快速"？
- 用户体验应该流畅 ← 不可测试，什么是"流畅"？

### 4.2 行为描述，非实现描述

规格**只描述系统的外部行为**，不涉及内部实现。

**禁止出现**：

- 类名（如 `UserService`、`NotificationController`）
- 函数名（如 `handleSubmit()`、`validateInput()`）
- 库名（如 `使用 Redis 缓存`、`通过 Kafka 发送消息`）
- 数据库表名（如 `写入 users 表`）
- 具体的技术方案（如 `使用 WebSocket 实现实时推送`）

**允许出现**：

- 用户可见的行为（如"系统发送通知"、"页面显示错误提示"）
- 业务规则（如"订单金额超过 1000 元时需要审批"）
- 性能约束（如"响应时间不超过 2 秒"）— 描述的是行为约束，不是实现方案

### 4.3 棕地开发 Delta 章节

当项目为棕地开发（在现有代码库上进行变更）时，规格**必须包含 Delta 章节**。

Delta 章节包含三个子章节：

| 子章节 | 说明 |
|--------|------|
| **新增** | 本次新增的功能、文件、接口 |
| **修改** | 本次修改的功能、文件、接口，附变更说明 |
| **不变** | 明确不受影响的功能、文件、接口 |

**"不变"子章节的意义**：明确列出不受影响的部分，防止 build 阶段误改，也帮助 review 阶段确认没有意外的副作用。

**判定棕地开发的信号**：

- 项目已有代码库（非空项目）
- 任务是对现有功能的修改或增强
- `.forge/specs/` 中已有其他功能的规格

### 4.4 "现状→变化"两段式结构（Current State / Proposed Change）

规格文档**必须包含** "Current State" 和 "Proposed Change" 两个部分。这是为了确保 spec 与实际代码保持一致，减少方案与现实冲突。

**Current State 部分要求**：

- **必须引用具体代码位置**：使用 `file:line` 格式（如 `src/auth.ts:42`）或函数名（如 `validateToken()`）指向相关代码
- **必须描述当前行为和结构**：说明相关模块/函数目前做什么、怎么组织的
- **AI 必须先读代码**：在填写 Current State 之前，AI 必须实际读取相关代码文件，不允许凭记忆或推测填写

**Proposed Change 部分要求**：

- **必须明确"要改变什么"**：逐项列出计划变更的内容
- **必须明确"不改变什么"**：逐项列出明确不受影响的部分及原因，防止 build 阶段误改

**合格示例**：

```markdown
## Current State

### 相关模块

| 模块/函数 | 位置 | 当前行为 |
|-----------|------|---------|
| validateToken() | src/auth.ts:42 | 仅验证 JWT 签名，不检查过期时间 |
| authMiddleware | src/middleware/auth.ts:15 | 调用 validateToken()，失败返回 401 |

### 当前结构概述

认证模块由 `src/auth.ts` 和 `src/middleware/auth.ts` 组成。
`validateToken()`（auth.ts:42）负责 JWT 签名验证，`authMiddleware`（auth.ts:15）
作为 Express 中间件调用它。当前不检查 token 过期时间。

## Proposed Change

### 要改变的

- `validateToken()`：增加过期时间检查逻辑
- 错误响应：过期 token 返回 401 + 特定错误码 `TOKEN_EXPIRED`

### 明确不改变的

- `authMiddleware` 的调用方式：不需要改，它只是透传 validateToken 的结果
- 登录流程：不受影响，token 生成逻辑不变
```

**不合格示例**：

- 没有 file:line 引用，只写"认证模块需要改进" ← 无法定位
- Current State 部分凭记忆写，与实际代码不一致 ← 会导致方案冲突
- 只写了"要改变什么"，没写"不改变什么" ← build 阶段可能误改

### 4.5 可卸载性（Reversibility）

规格文档**必须包含** "Reversibility" 部分，回答一个核心问题：**如果要回滚这个 feature，需要撤销哪些改动？**

**Reversibility 部分要求**：

- **回滚清单**：列出回滚时需要撤销的所有改动
- **挂载点清单**：列出 feature 的所有外部接入点。判据：删了这一项，feature 是否从用户/系统视角消失？

**意义**：提前思考可卸载性，能帮助发现隐藏的耦合和副作用。如果一个 feature 无法干净回滚，说明设计可能存在过度耦合。

## 5. 门禁：Spec 未锁定 → 阻断 `/forge build`

在标准路径和全量路径下，`/forge build` 启动前**必须检查** `.forge/specs/` 中是否存在锁定的规格。

**检查逻辑**：

1. 扫描 `.forge/specs/` 下所有 `spec.md` 文件。
2. 读取每个文件的 YAML frontmatter。
3. 检查与当前任务相关的 spec 的 `status` 字段。

**阻断行为**：

如果相关 spec 的 status 不是 `"locked"`，阻断 build 并输出：

```
🚫 Build 阻断：规格未锁定

当前任务的规格状态为 "draft"，需要先锁定规格才能开始 build。
请运行 /forge spec 完成规格的 Review 和 Lock 流程。

规格路径：.forge/specs/<feature>/spec.md
当前状态：draft
```

**轻量路径例外**：轻量路径不要求锁定的 spec，直接执行 build。

## 6. 执行流程

### 完整流程图

```
用户输入 /forge spec
        │
        ▼
  ┌─────────────┐
  │  读取上下文 │  decisions/、config.md、specs/
  └──────┬──────┘
         │
         ▼
  ┌─────────────┐
  │  Propose    │  生成规格草案
  │  生成草案   │
  └──────┬──────┘
         │
         ▼
  ┌─────────────┐     未通过
  │  Review     │────────────┐
  │  五项自检   │            │
  └──────┬──────┘            ▼
         │            ┌────────────┐
         │ 通过       │  自动修正  │
         │            │  重新自检  │
         │            └──────┬─────┘
         │                   │
         │◄──────────────────┘
         ▼
  ┌─────────────┐
  │  用户确认？ │
  └──────┬──────┘
    是 │     │ 否
       ▼     ▼
  ┌────┐  ┌──────────┐
  │Lock│  │ 修改草案  │──→ 回到 Review
  └──┬─┘  └──────────┘
     │
     ▼
  输出 .forge/specs/<feature>/spec.md
  status: "locked"
```

### Step 0：前置检查

检查 `.forge/` 目录是否存在：

- **不存在** → 提示：`⚠️ 未检测到 .forge/ 目录。请先运行 forge init 初始化项目。`
- **存在** → 继续执行。

### Step 1：读取上下文

按优先级读取：

1. `.forge/decisions/` — 提取已确认的决策（如有）
2. `.forge/config.md` — 获取项目配置
3. `.forge/specs/` — 扫描现有规格，识别相关功能

### Step 2：Propose

基于上下文生成规格草案（详见第 2 节 Step 1）。

### Step 3：Review

执行四项自检（详见第 2 节 Step 2）。

### Step 4：用户确认或修改

- **用户确认**（回复确认、是、ok、y 等）→ 进入 Lock。
- **用户提出修改意见** → 据此更新草案，回到 Review。
- **用户拒绝**（回复 n、否、不等）→ 规格保持 draft，等待进一步指示。

### Step 5：Lock

锁定规格（详见第 2 节 Step 3）。

## 7. 边界情况处理

### 7.1 无 decisions/ 文档

如果 `.forge/decisions/` 为空或不存在，跳过决策文档读取，直接基于用户输入和 config.md 生成草案。输出提示：

```
ℹ️ 未找到决策文档，将直接基于你的需求描述生成规格草案。
如需先进行多视角决策分析，可运行 /forge decide。
```

### 7.2 已有同名 spec

如果 `.forge/specs/<feature>/spec.md` 已存在：

- **status 为 draft** → 读取现有草案作为基础，在其上修改而非重新生成。
- **status 为 locked** → 提示：

```
⚠️ 该功能的规格已锁定：.forge/specs/<feature>/spec.md
如需修改，请先将 status 改为 "draft"，然后重新运行 /forge spec。
```

### 7.3 需求描述过于模糊

如果用户的需求描述过于模糊，无法生成有意义的可测试场景，追问一次：

```
需求描述不够具体，无法生成可测试的规格。请补充：
1. 这个功能要解决什么问题？
2. 目标用户是谁？
3. 有哪些关键的使用场景？
```

### 7.4 自检反复不通过

如果自检在自动修正后仍然不通过（连续 3 次），停止自动修正，将问题呈现给用户：

```
⚠️ 以下检查项在自动修正后仍未通过：
- 可测试性：需求 3 缺少可测试场景，无法自动补充

请提供更具体的场景描述，或确认是否接受当前状态。
```

### 7.5 无 `.forge/` 目录

提示先运行初始化：

```
⚠️ 未检测到 .forge/ 目录。请先运行 forge init 初始化项目。
```

## 8. 示例

### 示例 1：绿地项目（新项目）

任务："为订单系统添加批量导出功能"

生成的规格草案：

```markdown
---
feature: "order-batch-export"
status: "draft"
date: "2025-01-15"
---

## 目的

为订单管理系统提供批量导出功能，让运营人员能够按条件筛选并导出订单数据，用于对账和报表分析。

## 需求

### 需求 1：按条件筛选导出

运营人员可以按时间范围、订单状态、金额范围筛选订单并导出。

**场景**：

- 当运营人员选择"最近 7 天"并点击导出，则系统生成包含最近 7 天所有订单的文件并开始下载
- 当筛选结果为空，则系统提示"没有符合条件的订单"且不生成文件

### 需求 2：大数据量导出

当导出数据量较大时，系统应支持异步导出并通知用户。

**场景**：

- 当导出订单数超过 10000 条，则系统提示"导出任务已提交，完成后将通知你"并在后台处理
- 当后台导出完成，则系统发送通知并提供下载链接
- 当下载链接超过 24 小时，则链接失效并提示"链接已过期，请重新导出"

## 场景汇总

| 编号 | 场景 | 对应需求 |
|------|------|---------|
| S1 | 当运营人员选择"最近 7 天"并点击导出，则系统生成文件并开始下载 | 需求 1 |
| S2 | 当筛选结果为空，则提示"没有符合条件的订单" | 需求 1 |
| S3 | 当导出订单数超过 10000 条，则提示"导出任务已提交" | 需求 2 |
| S4 | 当后台导出完成，则发送通知并提供下载链接 | 需求 2 |
| S5 | 当下载链接超过 24 小时，则链接失效 | 需求 2 |

## 不做什么

- 不做导出模板自定义（固定格式）
- 不做定时自动导出（仅支持手动触发）
- 不做导出历史记录管理

## 反漂移声明

让运营人员能够按条件筛选并导出订单数据，大数据量时支持异步处理。

### 非目标代理信号

- 文件格式丰富度不是目标，固定格式能满足对账和报表需求即可
```

## 9. 已知 AI 失败模式

> 以下是 AI 在执行 `/forge spec` 时常见的失败模式。在生成和审查规格时，主动检查自己是否正在犯这些错误。

### 失败模式 1：不读现有代码就写 spec

| | |
|---|---|
| **错误行为** | 直接根据用户描述生成 spec，不读取项目中的相关代码文件，Current State 部分凭推测填写或留空 |
| **为什么这是错的** | 不读代码就无法准确描述当前状态，导致 spec 中的 Current State 与实际代码不一致。build 阶段按错误的 spec 实现，会产生与现有代码冲突的变更，增加返工成本 |
| **正确做法** | 在生成草案之前，先用工具读取与需求相关的代码文件，确认模块结构、函数签名和当前行为，然后用 file:line 引用填写 Current State |

### 失败模式 2：spec 与代码实际结构不一致

| | |
|---|---|
| **错误行为** | spec 中引用的文件路径、函数名、行号与实际代码不匹配。例如写 `src/auth.ts:42` 但该文件实际只有 30 行，或引用了不存在的函数名 |
| **为什么这是错的** | 不一致的引用会误导 build 阶段的 AI，导致它去修改错误的位置或创建不必要的新文件。review 阶段也无法正确验证变更是否符合 spec |
| **正确做法** | 每个 file:line 引用都必须经过实际读取验证。如果代码结构在 spec 编写期间发生了变化，重新读取并更新引用。在 Review 自检时，逐一确认引用的准确性 |

### 失败模式 3：遗漏"明确不做"边界

| | |
|---|---|
| **错误行为** | 只写了"要做什么"，没有写"不做什么"和"明确不改变什么"。Proposed Change 中缺少"明确不改变的"子章节，"不做什么"章节为空或过于笼统 |
| **为什么这是错的** | 没有明确边界，build 阶段的 AI 会"顺手"改动范围外的代码（如重构相邻模块、添加未要求的功能）。review 阶段也无法判断哪些改动是"超出范围"的 |
| **正确做法** | 在 Proposed Change 中明确列出"明确不改变的"条目并说明原因。在"不做什么"章节中列出用户可能期望但本次不实现的功能。边界越清晰，build 和 review 的质量越高 |
