# /forge test — 测试引擎

> **触发方式**：标准路径的第四步，全量路径的第六步，或用户直接输入 `/forge test`
> **职责**：系统化的三层验证，确保代码在单元测试、浏览器 QA 和完成前清单三个层面都通过验证
> **输出路径**：`.forge/progress/<topic>.md`（更新验证状态）

---

## 1. 概述

`/forge test` 通过三层验证（单元测试 → 浏览器级 QA → 完成前验证清单）对 build 和 review 阶段的产出进行系统化验证。每一层都有明确的通过标准，最终以 7 项完成前验证清单作为交付门禁。

**验证铁律**：没有运行验证命令 = 不能声明通过。拒绝"应该可以了"、"看起来没问题"、"和之前一样的逻辑"等非验证声明。唯一接受的完成证据是验证命令的实际输出。

---

## 2. 三层验证

### Layer 1 — 单元测试

**职责**：运行项目测试套件，确认所有测试通过且输出干净。

**执行步骤**：

1. 检测项目的测试框架和运行命令（从 `package.json`、`Makefile`、`Cargo.toml` 等配置文件中识别）。
2. 运行完整测试套件。
3. 检查测试输出：
   - 所有测试通过（零失败）
   - 无 warning（或仅有已知的、可忽略的 warning）
   - 无 error

**通过标准**：

```
✅ Layer 1 — 单元测试通过
  运行命令：npx vitest run
  结果：42 tests passed, 0 failed, 0 skipped
  Warning：0
  Error：0
```

**未通过时的处理**：

```
❌ Layer 1 — 单元测试未通过
  运行命令：npx vitest run
  结果：40 tests passed, 2 failed, 0 skipped

  失败的测试：
  1. ExportService > should handle async export — Expected: true, Received: false
  2. ExportRoute > should return 400 for invalid date — Timeout after 5000ms

请修复失败的测试后重新运行 /forge test。
```

### Layer 2 — 浏览器级 QA（条件触发）

**触发条件**：仅当项目为 Web 项目时执行。

**判定 Web 项目的信号**：

- `package.json` 中包含前端框架依赖（React、Vue、Svelte、Angular 等）
- 项目中存在 `.html`、`.tsx`、`.jsx`、`.vue`、`.svelte` 文件
- `.forge/config.md` 中的 `stack` 包含前端技术

**执行步骤**：

1. 读取 `.forge/specs/<feature>/spec.md` 中的场景汇总表。
2. 对每个涉及用户交互的场景，模拟用户操作。
3. 在关键步骤截图记录。
4. 对比实际行为与 Spec 中的预期结果。

**通过标准**：

```
✅ Layer 2 — 浏览器级 QA 通过
  场景 S1：选择"最近 7 天"并导出 — ✅ 文件下载成功
  场景 S2：筛选结果为空 — ✅ 显示"没有符合条件的订单"
  截图已保存：.forge/reviews/screenshots/
```

**非 Web 项目**：

```
ℹ️ Layer 2 — 浏览器级 QA 跳过（非 Web 项目）
```

### Layer 3 — 完成前验证清单

**职责**：逐项检查 7 项完成前验证清单，确保所有交付条件满足。

**CI 检查命令优先级**：

执行 Layer 3 清单前，读取 `.forge/config.md` YAML frontmatter 的 `ci_check_command` 字段：
- **如果 `ci_check_command` 非空**：执行该命令一次，覆盖清单项 1-4（测试、测试通过、类型检查、Lint）。从合并输出中提取各项的通过/失败状态，逐项报告。
- **如果 `ci_check_command` 为空或缺失**：按当前行为，为每个清单项分别运行对应的命令。

**7 项清单**：

| # | 检查项 | 验证方式 |
|---|--------|---------|
| 1 | **测试刚运行过** | 若 `ci_check_command` 非空，由 CI 命令统一覆盖；否则单独运行测试命令。不接受引用之前的结果 |
| 2 | **所有测试通过** | 若 `ci_check_command` 非空，从 CI 命令输出中提取测试结果；否则检查测试输出零失败 |
| 3 | **类型检查通过** | 若 `ci_check_command` 非空，从 CI 命令输出中提取类型检查结果；否则运行 `tsc --noEmit` 或等效命令 |
| 4 | **Lint 通过** | 若 `ci_check_command` 非空，从 CI 命令输出中提取 Lint 结果；否则运行 `eslint`/`biome` 或等效命令 |
| 5 | **验收标准逐条确认** | 对照 Spec 场景汇总表，每个场景有对应的通过证据 |
| 6 | **无遗留 TODO/FIXME** | 扫描本次变更的文件，无新增的 `TODO`、`FIXME`、`HACK`、`XXX` 注释 |
| 7 | **Progress 已更新** | `.forge/progress/<topic>.md` 中所有任务标记为已完成 |

**清单输出格式**：

使用 `ci_check_command` 时：

```
📋 完成前验证清单

ℹ️ 使用 ci_check_command: npm run check

✅ 1. 测试刚运行过（CI 命令在本次会话 14:35 运行）
✅ 2. 所有测试通过（42/42）
✅ 3. 类型检查通过（tsc --noEmit：0 errors）
✅ 4. Lint 通过（biome check：0 errors, 0 warnings）
✅ 5. 验收标准逐条确认（5/5 场景通过）
✅ 6. 无遗留 TODO/FIXME（扫描 6 个变更文件：0 个遗留项）
✅ 7. Progress 已更新（5/5 任务完成）

✅ 验证通过。下一步：/forge ship
```

未使用 `ci_check_command` 时：

```
📋 完成前验证清单

✅ 1. 测试刚运行过（本次会话 14:35 运行）
✅ 2. 所有测试通过（42/42）
✅ 3. 类型检查通过（tsc --noEmit：0 errors）
✅ 4. Lint 通过（eslint：0 errors, 0 warnings）
✅ 5. 验收标准逐条确认（5/5 场景通过）
✅ 6. 无遗留 TODO/FIXME（扫描 6 个变更文件：0 个遗留项）
✅ 7. Progress 已更新（5/5 任务完成）

✅ 验证通过。下一步：/forge ship
```

**任一项未通过**：

```
📋 完成前验证清单

✅ 1. 测试刚运行过（本次会话 14:35 运行）
✅ 2. 所有测试通过（42/42）
❌ 3. 类型检查未通过（tsc --noEmit：3 errors）
  - src/services/export.ts(42,5): error TS2345: Argument of type 'string' is not assignable...
✅ 4. Lint 通过
✅ 5. 验收标准逐条确认（5/5 场景通过）
❌ 6. 发现遗留 TODO/FIXME
  - src/jobs/async-export.ts 第 28 行：// TODO: add retry logic
✅ 7. Progress 已更新

❌ 验证未通过。请修复以上问题后重新运行 /forge test。
```

## 3. 验证铁律

声称工作完成却没有验证，不是效率，是不诚实。

**核心原则**：证据先于声明，永远如此。**违反这条规则的字面意思就是违反这条规则的精神。**

### 3.1 验证门函数

```
在声称任何状态或表达满意之前：

1. 识别：什么命令能证明这个声明？
2. 运行：执行完整命令（新鲜的、完整的）
3. 阅读：完整输出，检查退出码，计数失败项
4. 验证：输出是否确认了声明？
   - 如果否：陈述实际状态和证据
   - 如果是：带着证据陈述声明
5. 然后才能：做出声明

跳过任何一步 = 在撒谎，不是在验证
```

### 3.2 常见虚假声明对照表

| 声明 | 需要的证据 | 不算证据 |
|------|-----------|---------|
| "测试通过了" | 测试命令输出：0 failures | 之前的运行结果、"应该通过" |
| "Lint 干净了" | Lint 输出：0 errors | 部分检查、推断 |
| "构建成功了" | 构建命令：exit 0 | Lint 通过、日志看起来正常 |
| "Bug 修好了" | 测试原始症状：通过 | 代码改了、假设修好了 |
| "回归测试有效" | Red-Green 循环验证 | 测试只通过一次 |
| "Subagent 完成了" | VCS diff 显示变更 | Subagent 报告"成功" |
| "需求满足了" | 逐条对照清单 | 测试通过 ≠ 需求满足 |

### 3.3 Red Flag — 立即停下

出现以下任何信号时，**停下来，先运行验证**：

- 使用"应该"、"大概"、"看起来"
- 在验证之前表达满意（"好了！"、"完美！"、"搞定！"）
- 准备提交/推送/创建 PR 但还没运行验证
- 信任 Subagent 的成功报告而没有独立验证
- 依赖部分验证
- 想着"就这一次"
- 疲劳了想赶紧结束
- **任何暗示成功但没有运行验证命令的措辞**

### 3.4 合理化借口逐条反驳

| 借口 | 现实 |
|------|------|
| "应该可以了" | 运行验证命令 |
| "我很有信心" | 信心 ≠ 证据 |
| "就这一次" | 没有例外 |
| "Lint 通过了" | Lint ≠ 编译器 ≠ 测试 |
| "Subagent 说成功了" | 独立验证 |
| "我累了" | 疲劳 ≠ 借口 |
| "部分检查够了" | 部分证明不了什么 |
| "换个说法所以规则不适用" | 精神高于字面 |
| "上次测试通过了" | 上次不算，代码可能已经变了 |
| "和之前一样的逻辑" | 一样的逻辑也需要验证 |

### 3.5 拒绝引用之前的测试结果

即使上一步刚运行过测试，如果之后有任何代码变更（包括 refactor），测试结果就已过期。必须重新运行。

**判定规则**：

1. 记录最后一次测试运行的时间戳。
2. 记录最后一次代码变更的时间戳。
3. 如果代码变更时间 > 测试运行时间 → 测试结果过期，需要重新运行。

### 3.6 验证命令必须存在

如果项目没有配置测试命令、类型检查命令或 Lint 命令，不能跳过对应的清单项，而是提示配置：

```
⚠️ 未检测到类型检查命令。请在项目中配置 TypeScript 或等效的类型检查工具。
清单项 3（类型检查通过）无法验证。
```

## 4. 门禁：测试未通过 → 阻断 `/forge ship`

测试引擎的验证结果直接影响 `/forge ship` 的门禁检查。

**阻断条件**：

- Layer 1 单元测试未通过
- Layer 3 完成前验证清单任一项未通过

**阻断行为**：

```
🚫 Ship 阻断：测试未通过

以下验证项未通过：
  ❌ 类型检查：3 个类型错误
  ❌ 遗留 TODO/FIXME：1 个遗留项

请修复后重新运行 /forge test。
```

**放行条件**：Layer 1 通过 + Layer 3 所有 7 项通过。Layer 2（浏览器级 QA）为辅助验证，不阻断 ship。

## 5. 执行流程

### 完整流程图

```
用户输入 /forge test
        │
        ▼
  ┌─────────────┐
  │  前置检查    │  有代码变更？有测试配置？
  └──────┬──────┘
         │
         ▼
  ┌─────────────┐
  │  Layer 1    │  运行项目测试套件
  │  单元测试    │
  └──────┬──────┘
    通过 │     │ 失败
         │     ▼
         │   ❌ 报告失败，停止
         ▼
  ┌─────────────┐
  │  Layer 2    │  浏览器级 QA（条件触发）
  │  浏览器 QA  │
  └──────┬──────┘
         │
         ▼
  ┌─────────────┐
  │  Layer 3    │  7 项完成前验证清单
  │  验证清单    │
  └──────┬──────┘
    通过 │     │ 未通过
         │     ▼
         │   ❌ 报告未通过项
         ▼
  ✅ 验证通过
  下一步：/forge ship
```

### Step 0：前置检查

1. 检查 `.forge/` 目录是否存在 → 不存在则提示 `forge init`。
2. 检查是否有代码变更。
3. 检测项目的测试框架和运行命令。

### Step 1：Layer 1 — 单元测试

运行项目测试套件（详见第 2 节 Layer 1）。

### Step 2：Layer 2 — 浏览器级 QA

如果是 Web 项目，执行浏览器级 QA（详见第 2 节 Layer 2）。否则跳过。

### Step 3：Layer 3 — 完成前验证清单

逐项检查 7 项清单（详见第 2 节 Layer 3）。

### Step 4：输出结果

汇总三层验证结果，更新 `.forge/progress/<topic>.md` 的验证状态。

## 6. 边界情况处理

### 6.1 无测试框架

如果项目没有配置测试框架：

```
⚠️ 未检测到测试框架。请先配置测试框架（如 Vitest、Jest、pytest 等）。
Layer 1（单元测试）无法执行。
```

### 6.2 测试超时

如果测试运行超过合理时间（默认 5 分钟）：

```
⚠️ 测试运行超时（>5 分钟）。可能原因：
1. 测试中有未关闭的异步操作
2. 测试数据量过大
3. 存在死循环

请检查测试代码后重新运行。
```

### 6.3 部分清单项无法验证

如果某些清单项因为项目配置缺失而无法验证，标记为"无法验证"而非"通过"：

```
📋 完成前验证清单

✅ 1. 测试刚运行过
✅ 2. 所有测试通过
⚠️ 3. 类型检查：未配置（项目无 TypeScript）
⚠️ 4. Lint：未配置
✅ 5. 验收标准逐条确认
✅ 6. 无遗留 TODO/FIXME
✅ 7. Progress 已更新

⚠️ 2 项无法验证。建议配置类型检查和 Lint 工具。
其余 5 项全部通过。
```

### 6.4 无 `.forge/` 目录

提示先运行初始化：

```
⚠️ 未检测到 .forge/ 目录。请先运行 forge init 初始化项目。
```
