# Requirements Document

## Introduction

CLAUDE.md is generated once by `forge init` and never updated afterward. The knowledge system (`/forge learn`) accumulates data across sessions (instincts, known-failures, skill-feedback, metrics), but none of this feeds back into CLAUDE.md. This feature creates a **self-evolution mechanism** that distills "error-prevention rules" from accumulated knowledge and makes them available to Claude in every session via a dual-file architecture.

**Core principle**: Only add rules that "Claude would make mistakes without" — not knowledge dumps.

The mechanism uses a dual-file separation:
- **CLAUDE.md** (stable, generated by `forge init`): Gets a new Section 5 referencing evolved-rules.md
- **`.tinkerman/knowledge/evolved-rules.md`** (dynamic, maintained by `/forge learn`): Stores distilled error-prevention rules (max 15)

## Glossary

- **Evolved_Rules_File**: The file at `.tinkerman/knowledge/evolved-rules.md` that stores distilled error-prevention rules derived from accumulated knowledge data
- **Rule**: A single error-prevention entry in the Evolved_Rules_File, containing a title, content, prevents declaration, source reference, confidence score, and metadata
- **Rule_Distillation**: The transformation process that converts raw knowledge data (known-failures, instincts, skill-feedback, metrics) into concise error-prevention rules with explicit "prevents" declarations
- **Correction_Proposal**: A structured suggestion to add, update, or retire a rule in the Evolved_Rules_File, requiring user approval before application
- **Rule_Changelog**: A dedicated file at `.tinkerman/knowledge/rule-changelog.md` that records all rule additions, updates, and retirements with timestamps
- **Session_Start_Hook**: A hook in `hooks.json` that injects the content of evolved-rules.md into Claude's context at the beginning of each session
- **Forge_Learn_Skill**: The `/forge learn` SKILL.md that orchestrates knowledge extraction, including the new rule distillation stage
- **Init_Script**: The `scripts/init.sh` script that initializes project structure and processes template placeholders
- **Contract_Tests**: The test suite in `test/contract.test.ts` that validates cross-file consistency across the Forge project
- **Protection_Zone**: One of three access control levels (Frozen, Guarded, Open) defined in `config.md` that govern AI write permissions to `.tinkerman/` files
- **Confidence_Score**: A numeric value (0.3–0.9) indicating the reliability of a knowledge pattern or rule
- **Rule_Staleness**: A decay mechanism based on a `last_triggered` field that identifies rules not referenced in recent sessions

## Requirements

### Requirement 1: Evolved Rules Template File

**User Story:** As a Forge user, I want an evolved-rules.md template to exist in the templates directory, so that `forge init` can provision the file for new projects.

#### Acceptance Criteria

1. THE Evolved_Rules_File template SHALL exist at `templates/evolved-rules.md` with YAML frontmatter containing `updated`, `rule_count`, and `max_rules: 15` fields
2. WHEN `forge init` is executed, THE Init_Script SHALL copy the Evolved_Rules_File template to `.tinkerman/knowledge/evolved-rules.md` with `{{init_date}}` and `{{max_rules}}` placeholders replaced by actual values
3. THE Evolved_Rules_File template SHALL define the rule format as `### R{N}: {title}` with required fields: content, prevents, source, added, confidence, and last_triggered
4. THE Evolved_Rules_File template SHALL contain an empty rules section with a comment documenting the expected rule format

### Requirement 2: CLAUDE.md Section 5 — Self-Evolution Protocol

**User Story:** As a Forge user, I want CLAUDE.md to contain a self-evolution protocol section, so that Claude understands how to read and apply evolved rules in every session.

#### Acceptance Criteria

1. THE CLAUDE.md template SHALL contain a Section 5 titled "Self-Evolution Protocol" placed after the existing Section 4 (Knowledge Discipline) and before the "项目信息" section
2. THE CLAUDE.md template Section 5.1 SHALL instruct Claude to read `.tinkerman/knowledge/evolved-rules.md` at session start and treat its rules as project-specific error-prevention directives
3. THE CLAUDE.md template Section 5.2 SHALL enumerate the five categories of updatable knowledge: project-specific traps (from known-failures, occurrence >= 3), repeated correction patterns (from instincts, confidence >= 0.8), environment/tool quirks (from skill-feedback, frequency >= 3), cross-session behavior corrections (same issue across 3+ sessions), and rule friction adjustments (metrics showing 3+ session degradation trend)
4. THE CLAUDE.md template Section 5.3 SHALL define trigger conditions with explicit numeric thresholds for each category
5. THE CLAUDE.md template Section 5.4 SHALL define the correction protocol as a four-step process: propose rule with evidence, declare what error the rule prevents, present to user for approval, and log the change
6. THE CLAUDE.md template Section 5.5 SHALL define constraints: 15-rule cap, retirement policy for stale rules, and explicit protection of Sections 1–4 as owned by `forge init`
7. THE CLAUDE.md template Section 5 SHALL explicitly state that architecture descriptions, file path lists, general best practices, raw knowledge data, and standards enforced by existing tools are excluded from rule candidates

### Requirement 3: Rule Distillation Stage in Forge Learn

**User Story:** As a Forge user, I want `/forge learn` to automatically distill error-prevention rules from accumulated knowledge, so that high-value patterns are surfaced without manual curation.

#### Acceptance Criteria

1. THE Forge_Learn_Skill SHALL contain a new stage titled "Error-Prevention Rule Distillation" positioned after the "cross-project pattern detection" stage (Section 6.3) and before the "session cleanup" stage (Section 9 execution flow, before "会话层清理")
2. WHEN the rule distillation stage executes, THE Forge_Learn_Skill SHALL read four data sources: `.tinkerman/knowledge/known-failures.md`, `.tinkerman/knowledge/instincts.md`, `.tinkerman/knowledge/skill-feedback.md`, and `.tinkerman/knowledge/metrics.md`
3. WHEN a known-failure entry has occurrence count >= 3, THE Forge_Learn_Skill SHALL generate a Correction_Proposal for that pattern
4. WHEN an instinct pattern has Confidence_Score >= 0.8, THE Forge_Learn_Skill SHALL generate a Correction_Proposal for that pattern
5. WHEN a skill-feedback entry has frequency >= 3, THE Forge_Learn_Skill SHALL generate a Correction_Proposal for that pattern
6. WHEN the same issue appears corrected across 3 or more sessions (detected via session journals), THE Forge_Learn_Skill SHALL generate a Correction_Proposal for that pattern
7. WHEN metrics.md shows a degradation trend across 3 or more consecutive sessions for any quality dimension, THE Forge_Learn_Skill SHALL generate a Correction_Proposal to adjust or retire the friction-causing rule
8. EACH Correction_Proposal SHALL contain: the proposed rule text, the evidence source, a "prevents" declaration describing the specific error prevented, and a confidence score
9. THE Forge_Learn_Skill SHALL present all Correction_Proposals to the user for approval before writing to the Evolved_Rules_File
10. IF no knowledge entries meet any threshold, THEN THE Forge_Learn_Skill SHALL output a silent pass message and proceed to the next stage without generating proposals

### Requirement 4: Rule Capacity Management

**User Story:** As a Forge user, I want the evolved rules file to enforce a 15-rule cap with intelligent retirement, so that the instruction budget remains focused on high-value rules.

#### Acceptance Criteria

1. WHILE the Evolved_Rules_File contains 15 rules, THE Forge_Learn_Skill SHALL include a retirement proposal alongside any new rule proposal, identifying the lowest-value existing rule for removal
2. THE Forge_Learn_Skill SHALL calculate rule value based on confidence score and staleness (time since last_triggered), where rules not triggered in the last 5 sessions are candidates for retirement
3. WHEN a rule is retired, THE Forge_Learn_Skill SHALL record the retirement in the Rule_Changelog with the reason and date
4. THE Evolved_Rules_File `rule_count` frontmatter field SHALL always reflect the actual number of rules in the file
5. IF a new rule proposal has lower confidence than all existing rules and the file is at capacity, THEN THE Forge_Learn_Skill SHALL skip the proposal and log the reason

### Requirement 5: Rule Conflict Detection

**User Story:** As a Forge user, I want the system to detect conflicting rules before adding new ones, so that the evolved rules remain internally consistent.

#### Acceptance Criteria

1. WHEN a new Correction_Proposal is generated, THE Forge_Learn_Skill SHALL scan existing rules in the Evolved_Rules_File for potential conflicts by comparing the "prevents" declarations
2. IF a potential conflict is detected between a new proposal and an existing rule, THEN THE Forge_Learn_Skill SHALL present both rules to the user with an explanation of the conflict and ask the user to choose: keep existing, replace with new, or keep both
3. THE Forge_Learn_Skill SHALL treat two rules as potentially conflicting when they reference the same system component and have contradictory directives

### Requirement 6: Session Start Hook for Evolved Rules Injection

**User Story:** As a Forge user, I want evolved rules to be automatically loaded into Claude's context at session start, so that error-prevention rules are reliably available without manual action.

#### Acceptance Criteria

1. THE hooks.json SessionStart event SHALL contain a hook entry that outputs the content of `.tinkerman/knowledge/evolved-rules.md` when the file exists
2. THE Session_Start_Hook SHALL use a conditional check (`if [ -f ... ]`) so that projects without evolved-rules.md do not produce errors
3. THE Session_Start_Hook SHALL include a timeout value that is a positive integer
4. THE Session_Start_Hook command SHALL use a conditional file existence check (`if [ -f ... ]`) as its safety mechanism, which is sufficient since the conditional prevents any error output when the file is absent

### Requirement 7: Stop Hook for Pending Correction Proposals

**User Story:** As a Forge user, I want to be reminded about pending correction proposals when a session ends, so that I do not forget to review and approve proposed rule changes.

#### Acceptance Criteria

1. THE hooks.json Stop event SHALL contain a hook entry that checks for pending correction proposals and outputs a reminder message when proposals exist
2. THE Stop hook reminder SHALL indicate the number of pending proposals and suggest running `/forge learn` to review them

### Requirement 8: Rule Changelog

**User Story:** As a Forge user, I want a dedicated changelog for rule changes, so that I can audit the evolution history of error-prevention rules without polluting other knowledge files.

#### Acceptance Criteria

1. THE Rule_Changelog SHALL be stored at `.tinkerman/knowledge/rule-changelog.md` as a dedicated file separate from skill-feedback.md
2. WHEN a rule is added to the Evolved_Rules_File, THE Forge_Learn_Skill SHALL append an entry to the Rule_Changelog with the rule title, action (added), date, source, and confidence
3. WHEN a rule is retired from the Evolved_Rules_File, THE Forge_Learn_Skill SHALL append an entry to the Rule_Changelog with the rule title, action (retired), date, and reason
4. WHEN a rule is updated in the Evolved_Rules_File, THE Forge_Learn_Skill SHALL append an entry to the Rule_Changelog with the rule title, action (updated), date, and description of the change
5. THE Rule_Changelog template SHALL exist at `templates/rule-changelog.md` with YAML frontmatter containing an `updated` field

### Requirement 9: Protection Zone Configuration

**User Story:** As a Forge user, I want evolved-rules.md to be in the Guarded protection zone, so that AI can append and update rules through the learn process but cannot arbitrarily delete rules outside of maintenance.

#### Acceptance Criteria

1. THE config.md template SHALL list `.tinkerman/knowledge/evolved-rules.md` in the Guarded zone with the annotation: "only updatable by `/forge learn` rule distillation, not deletable outside maintenance"
2. THE config.md template SHALL list `.tinkerman/knowledge/rule-changelog.md` in the Guarded zone with append-only semantics
3. THE CLAUDE.md template Section 5.5 SHALL reference the Guarded zone protection for evolved-rules.md

### Requirement 10: Contract Test Coverage

**User Story:** As a developer, I want contract tests to validate the evolved-rules.md template and related cross-file consistency, so that regressions are caught automatically.

#### Acceptance Criteria

1. THE Contract_Tests SHALL verify that `templates/evolved-rules.md` exists in the knowledge templates test group
2. THE Contract_Tests SHALL verify that `templates/rule-changelog.md` exists in the knowledge templates test group
3. THE Contract_Tests SHALL verify that the CLAUDE.md template contains a "Self-Evolution Protocol" section or equivalent heading
4. THE Contract_Tests SHALL verify that hooks.json SessionStart contains a hook entry referencing `evolved-rules.md`
5. THE Contract_Tests SHALL verify that the evolved-rules.md template contains the required YAML frontmatter fields (`updated`, `rule_count`, `max_rules`)

### Requirement 11: Init Script Placeholder Handling

**User Story:** As a developer, I want init.sh to correctly process evolved-rules.md template placeholders, so that newly initialized projects have a properly configured evolved rules file.

#### Acceptance Criteria

1. WHEN `forge init` processes the evolved-rules.md template, THE Init_Script SHALL replace `{{init_date}}` with the current date in YYYY-MM-DD format
2. WHEN `forge init` processes the evolved-rules.md template, THE Init_Script SHALL replace `{{max_rules}}` with the configured maximum rule count (default 15)
3. THE Init_Script SHALL copy the processed evolved-rules.md to `.tinkerman/knowledge/evolved-rules.md`
4. THE Init_Script SHALL copy the rule-changelog.md template to `.tinkerman/knowledge/rule-changelog.md` with `{{init_date}}` replaced

### Requirement 12: Project Root CLAUDE.md Synchronization

**User Story:** As a developer, I want the project root CLAUDE.md to include the Section 5 self-evolution protocol, so that the development repository's own CLAUDE.md stays in sync with the template.

#### Acceptance Criteria

1. THE project root CLAUDE.md SHALL contain a Section 5 that matches the content structure defined in the CLAUDE.md template
2. THE project root CLAUDE.md Section 5 SHALL reference `.tinkerman/knowledge/evolved-rules.md` as the location of evolved rules

### Requirement 13: Rule Staleness and Decay

**User Story:** As a Forge user, I want rules that have not been triggered recently to be flagged for review, so that the evolved rules file does not accumulate stale directives.

#### Acceptance Criteria

1. EACH Rule in the Evolved_Rules_File SHALL have a `last_triggered` field recording the date when the rule was last referenced during a session
2. WHEN the rule distillation stage executes, THE Forge_Learn_Skill SHALL identify rules where `last_triggered` is older than 5 sessions ago and flag them as staleness candidates
3. WHEN a rule is flagged as stale, THE Forge_Learn_Skill SHALL include it in the retirement proposals presented to the user, with the staleness reason
4. THE Session_Start_Hook or the Forge_Learn_Skill SHALL update the `last_triggered` field of rules that were actively referenced during a session

### Requirement 14: Transformation Process Specification

**User Story:** As a Forge user, I want the rule distillation to follow a clear transformation process, so that raw knowledge is consistently converted into actionable error-prevention rules.

#### Acceptance Criteria

1. THE Forge_Learn_Skill rule distillation stage SHALL transform each qualifying knowledge entry through three steps: extract the raw pattern, distill into a concise rule statement, and declare what specific error the rule prevents
2. EACH distilled rule SHALL answer the question "what error does this prevent" with a specific, testable failure scenario
3. THE Forge_Learn_Skill SHALL exclude from rule candidates: architecture descriptions inferable from code, file path lists, general best practices Claude already knows, raw knowledge data, and standards enforced by existing tools (e.g., Biome code style)
4. FOR ALL valid Rule objects, parsing the Evolved_Rules_File then printing it back SHALL produce an equivalent file (round-trip property)
